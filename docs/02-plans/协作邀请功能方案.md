# 协作邀请功能方案

> 邀请码机制：授权人通过邮箱或用户名精确查找对方用户，发送协作邀请并生成 6 位邀请码，对方在首页收到邀请信号后输入邀请码完成接受。
>
> 修订记录（2026-09-30）：明确本方案**整体替代**现有 authorization_codes 授权码体系（旧体系未进入生产，无数据迁移负担）；新增「1.3 与现有授权码体系的关系」「4. 授权执行设计」两节；修正日志表复用方式、重复邀请校验、invite_code 脱敏、时间函数约定；补齐迁移、测试、路由清单。
>
> 修订记录（2026-09-30 二）：协作时长由"接受后起算 N 天"改为**授权人指定起止时间（精确到分钟）**，协作时段为固定窗口、与接受时刻无关；`collaboration_days` / `collaboration_expires_at` 字段由 `collaboration_start_at` / `collaboration_end_at` 取代。

## 1. 功能概述

协作邀请功能允许礼簿所有者（授权人）邀请非家庭成员的协作人员在指定时间段内协助管理特定礼簿。核心流程：

1. 授权人在礼簿页面点击「协助邀请」，输入对方**注册邮箱或用户名**精确查找用户
2. 设置权限和**协作起止时间**（精确到分钟），点击发送 → 系统生成 **6 位邀请码**，同时向对方发送**邀请信号**
3. 邀请信号 **10 分钟内有效**，对方登录后在**首页**看到「接受协助邀请」按钮
4. 点击按钮后显示邀请码输入框，输入 6 位邀请码确认身份，接受邀请；或点击「拒绝」直接拒绝邀请
5. 授权人可随时撤销授权

### 1.1 设计要点

- **账户精确查找**：支持对方**注册邮箱或用户名**精确查找，二者均能唯一确定账户，避免姓名重复导致的误邀；对方忘记注册邮箱时可用用户名兜底
- **6 位邀请码**：防止查找输错时误绑，对方收到邀请信号后需核对邀请码确认
- **10 分钟信号有效期**：邀请信号仅在 10 分钟内展示在首页，超时需重新发送
- **协作时段固定窗口**：起止时间由授权人指定（精确到分钟），与接受时刻无关；对方在开始前接受邀请的，时段开始后访问自动生效，无需再次激活

### 1.2 与家庭成员的区别

| 维度 | 家庭成员 | 协作人员 |
|------|---------|---------|
| 关系 | 长期家庭关系 | 临时协作关系 |
| 范围 | 可访问所有礼簿 | 仅访问指定礼簿 |
| 时间 | 无期限 | 有明确起止时间（精确到分钟） |
| 加入方式 | 家庭组邀请码 | 账户查找 + 邀请码确认 |

### 1.3 与现有授权码体系的关系（整体替代）

项目现有基于 `authorization_codes` 的礼簿授权码机制（`server/app/api/authorization.py` 生成 16 位授权码、被授权人在 AuthorizationPage 输入绑定、GuestbookPage 的协助邀请弹窗），**未进入生产环境，本方案对其进行整体替代，不做数据迁移**。

**替代差异对照**：

| 维度 | 旧授权码体系 | 本方案 |
|------|-------------|--------|
| 被授权人确定方式 | 用户名模糊搜索 + 账号 ID | 邮箱/用户名**精确**查找 |
| 授权确认方式 | 16 位码由对方主动输入绑定 | 系统推送邀请信号 + 6 位邀请码确认 + 可拒绝 |
| 协作时段 | 生成授权码时定死 expires_at | 授权人指定**起止时间**（精确到分钟），接受不改变时段 |
| 管理入口 | AuthorizationPage | CollaborationPage + 首页邀请信号 |
| 权限执行 | 仅 proxy-records 一处，且不区分 permissions | 统一访问依赖，按 permissions 强制（见第 4 节） |

**实施时同步下线旧体系**：

- 后端删除：`server/app/api/authorization.py`、`server/app/schemas/authorization_code.py`、`server/app/models/authorization_code.py`；`guestbook.py`、`user.py` 移除 `authorization_codes` 关系；alembic 迁移删除 `authorization_codes` 表
- 日志表改造：`authorization_action_logs` 删除 `authorization_code_id` 列及相关旧列，新增 `invite_id` 列（见 2.2）
- 前端删除：`AuthorizationPage.tsx` 及路由、`GenerateAuthCodeModal`（如仅服务于旧体系）、`api-client.ts` / `useQueries.ts` 中授权码相关函数与 hooks
- 执行点改接：原 `proxy-records` 中的 AuthorizationCode 校验改走第 4 节的统一访问依赖
- 旧 `GET /users/search` 接口（`auth.py`）若仍有其他页面调用方则保留，否则一并下线

## 2. 数据模型

### 2.1 CollaborationInvite（协作邀请）

**文件**：`server/app/models/collaboration_invite.py`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer, PK | 自增主键 |
| inviter_id | Integer, FK→users.id | 邀请人（礼簿所有者），CASCADE 删除 |
| invitee_id | Integer, FK→users.id | 被邀请人（协作人员），CASCADE 删除 |
| guestbook_id | Integer, FK→guestbooks.id | 关联礼簿 |
| invite_code | String(6), indexed | 6 位数字邀请码（明文存储，仅短期有效） |
| permissions | String(10), default "record" | 权限类型：record / reconcile / both |
| status | String(10), default "pending" | 状态：pending / accepted / rejected / revoked / expired |
| signal_expires_at | DateTime | 邀请信号过期时间（创建时间 + 10 分钟） |
| collaboration_start_at | DateTime | 协作开始时间（授权人指定，精确到分钟） |
| collaboration_end_at | DateTime | 协作结束时间（授权人指定，精确到分钟） |
| accepted_at | DateTime, nullable | 接受时间（接受不改变起止时段） |
| created_at | DateTime | 创建时间 |

**约束**：

- 同一邀请人对同一被邀请人、同一礼簿，最多存在一条 `pending` 邀请（防重复发送）。应用层先校验，数据库层加 **partial unique index** 兜底并发双发：`UNIQUE(inviter_id, invitee_id, guestbook_id) WHERE status = 'pending'`（SQLite / PostgreSQL 均支持）
- 同一邀请人对同一被邀请人、同一礼簿，不允许同时存在未结束的 `accepted` 协作（发送邀请时校验，已存在则拒绝并提示"对方已在协作中"）

**索引**：

- `invitee_id + status` 复合索引（首页查询待处理邀请）
- `invite_code` 索引（接受邀请时查找）
- `inviter_id + guestbook_id` 复合索引（查询某礼簿的邀请列表）
- partial unique index（见上）

**礼簿删除说明**：礼簿删除为软删（`is_deleted` 标记），外键级联不会触发；协作访问统一在访问依赖中校验 `is_deleted == False`（见第 4 节），软删礼簿对协作人员返回 404。

**数据隔离**：邀请人查询过滤 `inviter_id == current_user.id`；被邀请人查询过滤 `invitee_id == current_user.id`。

### 2.2 AuthorizationActionLog（操作日志，改造现有表）

**文件**：`server/app/models/authorization_action_log.py`（改造）

现有 `authorization_action_logs` 表的 `authorization_code_id` 为 NOT NULL 外键，无法直接复用。因旧体系未进入生产，直接改造该表：

**删除列**：`authorization_code_id`、`client_id`、`record_id`、`grantee_user_id`（均绑定旧体系）

**保留/新增列**：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer, PK | 自增主键 |
| invite_id | Integer, FK→collaboration_invites.id, NOT NULL, index | 关联协作邀请，CASCADE 删除 |
| action_type | String(30) | SEND / ACCEPT / REJECT / REVOKE |
| operator_name | String(50), nullable | 操作人昵称/用户名 |
| detail | Text, nullable | 操作详情描述 |
| created_at | DateTime, index | 操作时间（`app.core.time.utcnow`） |

### 2.3 状态流转

```
         发送
          ↓
      ┌──────────┐
      │ pending  │ ←── 初始状态（信号 10 分钟有效）
      └────┬─────┘
           │
     ┌─────┼──────────┬──────────┐
     ↓     ↓          ↓          ↓
┌──────────┐ ┌─────────┐ ┌────────┐ ┌─────────┐
│ accepted │ │ rejected│ │revoked │ │expired  │
└────┬─────┘ └─────────┘ └────────┘ └─────────┘
     │
     ↓
┌────────┐
│revoked │  （accepted 状态也可撤销）
└────────┘
```

- **pending**：已发送，等待对方接受或拒绝（信号 10 分钟内可见）→ 可取消邀请
- **accepted**：对方已接受邀请（协作时段为授权人指定的固定窗口，与接受时刻无关）→ 可撤销授权
- **rejected**：对方已拒绝邀请（终态）
- **revoked**：已被授权人撤销（pending 取消邀请 或 accepted 撤销授权）
- **expired**：信号超时（10 分钟内未操作）或协作结束时间到达（`collaboration_end_at < utcnow()`），查询时自动从 pending / accepted 懒标记为 expired（终态）

**注意**：信号过期（pending → expired）与协作到期（accepted → expired）是两个独立触发点，共用同一终态。信号过期后需重新发送邀请；协作到期后协作权限即时失效（访问校验见第 4 节）。对方在协作时段开始前接受邀请的，时段开始后方可访问，无需额外激活。

## 3. 后端 API

**文件**：`server/app/api/collaboration.py`
**路由前缀**：`/api/collaboration`
**时间函数**：一律使用 `app.core.time.utcnow()`（项目统一封装），不使用 `datetime.utcnow()`

### 3.1 通过邮箱或用户名查找用户

```
GET /api/collaboration/search?keyword=zhangsan
```

**查询参数**：

- `keyword`（必填）：精确匹配用户**注册邮箱或用户名**（大小写不敏感），命中其一即可

**响应**：

```json
{
  "id": 5,
  "username": "zhangsan",
  "email": "user@example.com"
}
```

**业务逻辑**：

1. 精确匹配邮箱或用户名查找用户（`email == keyword` OR `username == keyword`，均忽略大小写）
2. 不能查找自己（`id != current_user.id`）
3. 找不到时返回 404，不暴露用户是否存在（统一返回"未找到该邮箱或用户名对应的用户"）

### 3.2 发送协作邀请

```
POST /api/collaboration/invites
```

**请求体**（CollaborationInviteCreate）：

```json
{
  "invitee_keyword": "user@example.com",
  "guestbook_id": 1,
  "permissions": "record",
  "collaboration_start_at": "2026-10-01T09:00",
  "collaboration_end_at": "2026-10-08T21:00"
}
```

**响应**：

```json
{
  "id": 1,
  "invite_code": "385721",
  "invitee_email": "user@example.com",
  "signal_expires_at": "2026-09-30T10:10:00",
  "collaboration_start_at": "2026-10-01T09:00:00",
  "collaboration_end_at": "2026-10-08T21:00:00"
}
```

**业务逻辑**：

1. 通过 keyword 精确查找被邀请人（同 3.1 逻辑）
2. 验证礼簿存在且属于当前用户（`owner_id == current_user.id`，`is_deleted == False`）
3. 验证协作时段：`collaboration_end_at > collaboration_start_at`，且 `collaboration_start_at >= utcnow()`（最早从当前时刻开始；前端默认开始=当前时间、结束=当前时间 + 7 天）
4. 查重：
   - 已存在 `inviter_id + invitee_id + guestbook_id + status=pending` 的邀请 → 拒绝（"邀请已发送，请等待对方处理"）
   - 已存在 `inviter_id + invitee_id + guestbook_id + status=accepted` 且 `collaboration_end_at > utcnow()` 的协作 → 拒绝（"对方已在协作中，如需调整请先撤销原授权"）
5. 生成 6 位数字邀请码：`secrets.randbelow(1000000)` 补零至 6 位
6. 计算信号过期时间：`utcnow() + timedelta(minutes=10)`
7. 写入 `CollaborationInvite`（status=pending，`accepted_at=null`，起止时间原样存入）
8. 写入 `AuthorizationActionLog`（action_type=SEND）
9. 返回邀请码（仅此时展示一次，供授权人告知对方核对）

### 3.3 查询我的待处理邀请（首页用）

```
GET /api/collaboration/invites/pending
```

**响应**：`CollaborationInvitePendingResponse[]`

```json
[
  {
    "id": 1,
    "inviter_id": 2,
    "inviter_username": "李四",
    "guestbook_id": 1,
    "guestbook_name": "婚礼礼金",
    "permissions": "record",
    "signal_expires_at": "2026-09-30T10:10:00",
    "created_at": "2026-09-30T10:00:00"
  }
]
```

**业务逻辑**：

1. 查询 `invitee_id == current_user.id` 且 `status == "pending"`
2. 查询时自动将 `signal_expires_at < utcnow()` 的记录标记为 expired
3. 关联查询邀请人用户名和礼簿名称
4. 按 `created_at DESC` 排序

### 3.4 接受邀请

```
POST /api/collaboration/invites/accept
```

**请求体**（CollaborationInviteAcceptRequest）：

```json
{
  "invite_id": 1,
  "invite_code": "385721"
}
```

**响应**：

```json
{
  "message": "已接受协作邀请",
  "guestbook_id": 1,
  "permissions": "record",
  "collaboration_start_at": "2026-10-01T09:00:00",
  "collaboration_end_at": "2026-10-08T21:00:00"
}
```

**业务逻辑**：

1. 按 `invite_id` 查找邀请，验证 `invitee_id == current_user.id`
2. 验证状态为 pending
3. 验证信号未过期（`signal_expires_at > utcnow()`），否则标记 expired 并拒绝
4. 验证邀请码匹配（`invite_code == 请求的 invite_code`）
5. 更新状态为 accepted，记录 `accepted_at = utcnow()`
6. **无需计算协作截止时间**：起止时间由授权人指定并已存储，接受时刻不影响协作时段
7. 写入 `AuthorizationActionLog`（action_type=ACCEPT）
8. 协作关系即时生效，但**仅在协作时段内可访问**；时段开始前访问提示"协作尚未开始"（见第 4 节）

### 3.5 拒绝邀请

```
POST /api/collaboration/invites/{invite_id}/reject
```

**响应**：`{ "message": "邀请已拒绝" }`

**业务逻辑**：

1. 按 `invite_id` 查找邀请，验证 `invitee_id == current_user.id`
2. 验证状态为 pending（信号过期后会自动标记为 expired，此处无需额外检查）
3. 更新状态为 rejected
4. 写入 `AuthorizationActionLog`（action_type=REJECT）

### 3.6 查询我发出的邀请列表

```
GET /api/collaboration/invites?guestbook_id=1&status=active
```

**查询参数**：

- `guestbook_id`（可选）：按礼簿筛选
- `status`（可选）：按状态筛选（active 表示 pending + accepted）

**响应**：`CollaborationInviteResponse[]`

**业务逻辑**：

1. 查询 `inviter_id == current_user.id`，查询时自动将过期的 pending 标记为 expired、将到期的 accepted 标记为 expired
2. **invite_code 脱敏**：仅当记录 `status == "pending"` 且信号未过期时返回明文邀请码，其余状态一律返回 `null`（历史邀请不再暴露邀请码）

### 3.7 查询我接受的协作列表

```
GET /api/collaboration/invites/accepted
```

**响应**：`CollaborationInviteAcceptedResponse[]`

```json
[
  {
    "id": 1,
    "inviter_id": 2,
    "inviter_username": "李四",
    "guestbook_id": 1,
    "guestbook_name": "婚礼礼金",
    "permissions": "record",
    "collaboration_start_at": "2026-10-01T09:00:00",
    "collaboration_end_at": "2026-10-08T21:00:00",
    "accepted_at": "2026-09-30T10:05:00"
  }
]
```

**业务逻辑**：

1. 查询 `invitee_id == current_user.id` 且 `status == "accepted"`
2. 查询时自动将 `collaboration_end_at < utcnow()` 的记录标记为 expired（协作到期，访问权限即时失效）
3. 关联查询邀请人用户名和礼簿名称
4. 按 `accepted_at DESC` 排序
5. 前端按起止时间与当前时间计算展示状态：`未开始`（now < start_at）/ `协作中`（start_at ≤ now ≤ end_at）/ `已过期`（由后端懒标记）

### 3.8 撤销邀请（取消邀请 / 撤销授权）

```
POST /api/collaboration/invites/{invite_id}/revoke
```

**响应**：`{ "message": "邀请已撤销" }` 或 `{ "message": "授权已撤销" }`

**业务逻辑**：

1. 验证邀请的 `inviter_id == current_user.id`
2. 验证状态为 pending 或 accepted（expired 和 revoked 不可操作）
3. 更新状态为 revoked
4. 写入 `AuthorizationActionLog`（action_type=REVOKE）

**场景说明**：

- **pending 状态**：取消邀请（对方尚未接受）
- **accepted 状态**：撤销授权（协作期间终止协作关系，访问权限即时失效）

前端根据状态显示不同按钮文案和确认提示。

### 3.9 查询操作日志

```
GET /api/collaboration/invites/{invite_id}/logs
```

**响应**：`AuthorizationActionLogResponse[]`

## 4. 授权执行设计（协作访问通路）

> 本节回答"对方接受邀请后如何实际访问礼簿"。现状所有礼簿/记录接口均按 `owner_id == current_user.id` 硬过滤，协作人员无法访问他人礼簿；本方案将协作权限接入一个**统一访问依赖**，并明确端点与权限的映射。

### 4.1 统一访问依赖

**新文件**：`server/app/core/guestbook_access.py`

```python
async def get_guestbook_access(db, current_user, guestbook_id) -> GuestbookAccess | None
```

`GuestbookAccess` 数据结构：

| 字段 | 说明 |
|------|------|
| guestbook | Guestbook ORM 对象 |
| role | "owner" / "family" / "collaborator" |
| permissions | collaborator 时取邀请值（record / reconcile / both）；owner / family 时为 None（不受协作权限限制） |

**判定顺序**（先命中先返回）：

1. **owner**：`Guestbook.owner_id == current_user.id` 且 `is_deleted == False` → role=owner
2. **family**：礼簿所有者的 FamilyGroup 存在，且当前用户为其 active 成员 → role=family（与现有 proxy-records 家庭成员判定一致）
3. **collaborator**：存在 `invitee_id == current_user.id`、`guestbook_id` 匹配、`status == "accepted"` 且 `collaboration_start_at <= utcnow() <= collaboration_end_at` 的邀请（`end_at` 已过则懒标记 expired）→ role=collaborator
4. 礼簿不存在或已软删 → 404；存在但无任何授权 → 403

### 4.2 端点与权限映射

协作相关端点从 owner 硬过滤改为走 `get_guestbook_access`，按下表强制：

| 端点范围 | owner | family | collaborator: record | collaborator: reconcile | collaborator: both |
|---------|-------|--------|---------------------|------------------------|-------------------|
| 礼簿只读（详情、summary、记录列表、账户汇总等 GET） | ✓ | ✓ | ✗ | ✓ | ✓ |
| 对账（PATCH `/gb-records/{id}/check`、batch-check） | ✓ | ✓ | ✗ | ✓ | ✓ |
| 录入（POST `/guestbooks/{id}/proxy-records`） | ✓ | ✓ | ✓ | ✗ | ✓ |
| 礼簿管理（改 / 删 / 关闭 / 归档、协助邀请） | ✓ | ✗ | ✗ | ✗ | ✗ |

**规则**：

- 权限不满足 → 403，提示"无权限执行此操作"
- 协作被撤销或已到期（懒检测）→ 403，提示"协作授权已失效或已到期"
- 协作时段未开始（`utcnow() < collaboration_start_at`）→ 403，提示"协作尚未开始，开始时间为 X"（对方已接受但未到开始时间）
- 礼簿已归档 → 仅禁止录入（维持现状），只读与对账仍允许
- 家庭成员的只读/对账访问随本次改造一并放行（与"家庭成员可访问所有礼簿"的设计一致）

### 4.3 校验时机

不引入定时任务。所有协作访问在**每次请求时实时校验**：`status == "accepted"` 且 `collaboration_start_at <= utcnow() <= collaboration_end_at`；被撤销（revoked）、已到期或已懒标记 expired 的授权即时失效，协作人员下一次请求即被拦截。时段开始为自然生效，无需激活动作。

### 4.4 角色重叠

同一用户同时是家庭成员和协作人员时，按**家庭成员**处理（判定顺序在先），协作授权仅作补充。

### 4.5 前端受限视图

协作人员进入他人礼簿时：

- 顶部状态标识（数据源：`/collaboration/invites/accepted`）：
  - 时段内：「协作中 · 至 MM-DD HH:mm 结束」
  - 未到开始时间：「协作未开始 · MM-DD HH:mm 开始」
- 隐藏：礼簿设置、删除、归档、协助邀请等管理入口
- 对账/录入按钮按 permissions 显示；后端已按 4.2 拦截，前端隐藏仅为体验优化
- 入口：CollaborationPage「我接受的协作」列表 → 点击礼簿进入受限视图

## 8. 安全设计

### 8.1 邀请码生成

- 使用 `secrets.randbelow(1000000)` 生成 6 位数字，补零至 6 位
- 碰撞概率：100 万分之一，对于短期有效的邀请码足够安全
- 数据库不加全局 UNIQUE 约束；pending 唯一性由 partial unique index（inviter + invitee + guestbook）保证（见 2.1）

### 8.2 账户查找

- 精确匹配（邮箱或用户名），不支持模糊搜索，防止枚举用户
- 找不到时返回统一错误信息，不暴露用户是否存在
- 不能查找自己

### 8.3 数据隔离

- 邀请人查询：强制 `inviter_id == current_user.id`
- 被邀请人查询：强制 `invitee_id == current_user.id`
- 接受邀请：同时验证 `invitee_id` 和 `invite_code`
- 礼簿访问：强制走统一访问依赖（第 4 节），协作身份每次请求实时校验

### 8.4 有效期检测

**信号过期**（10 分钟）：

- 邀请信号固定 10 分钟有效，不可配置
- 采用懒检测策略：查询时自动将过期的 pending 标记为 expired
- 超时后首页不再展示该邀请，授权人需重新发送

**协作时段**（起止时间，精确到分钟）：

- 协作时段由授权人在发送邀请时指定（`collaboration_start_at` / `collaboration_end_at`），与接受时刻无关；开始时间不得早于发送时刻
- 采用懒检测策略：查询列表和访问校验时，自动将 `collaboration_end_at < utcnow()` 的记录标记为 expired
- 对方在时段开始前接受邀请的，开始时间到达前访问被拦截（403「协作尚未开始」）；时段开始访问自动生效，无需激活动作
- 协作到期/撤销即时生效：协作人员下一次访问即被统一访问依赖拦截（4.3），无需定时任务

### 8.5 时区处理

后端使用 `app.core.time.utcnow()`（项目统一封装）计算时间，所有时间字段存储为无时区的 UTC 时间。前端 `datetime-local` 输入的是用户本地时间，提交时转换为 UTC ISO 字符串，展示时按本地时区回显。
