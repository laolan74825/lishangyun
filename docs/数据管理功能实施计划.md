### 1.2.4 data_snapshot 字段 JSON 结构规范

> `data_snapshot` 存储待审批操作的数据快照，审批通过后反序列化写入业务表。采用 JSON 字符串存储于 Text 字段，应用层负责序列化/反序列化。

**CREATE 操作（新增记录）：**

```json
{
  "target_table": "daily_record",
  "data": {
    "person_name": "张三",
    "amount": 50000,
    "event_type": "婚礼",
    "payment_method": "wechat",
    "event_date": "2026-10-01",
    "type": "in"
  }
}
```

> 审批通过后，系统将 `data` 对象写入 `target_table` 对应的业务表。`data` 中字段名与业务表列名一致。

**UPDATE 操作（修改记录）：**

```json
{
  "target_table": "person",
  "target_id": 42,
  "before": { "name": "张三", "phone": "13800000000" },
  "after": { "name": "张三", "phone": "13900000000" }
}
```

> 审批通过后，系统将 `after` 对象写入 `target_table` 中 `id = target_id` 的记录。`before` 用于审批时对比展示。涉及 `sync_version` 的表（`daily_record`/`person`）需在 `after` 中包含递增后的 `sync_version`。

**DELETE 操作（删除记录）：**

```json
{
  "target_table": "gb_record",
  "target_id": 108,
  "before": { "guest_name": "李四", "amount": 20000, "guestbook_id": 5 }
}
```

> 审批通过后，系统对 `target_table` 中 `id = target_id` 的记录执行软删除（`is_deleted=true, deleted_at=now()`）。`before` 用于审计追溯。

**前端 PendingApproval 类型需同步修正（与 §1.2.2 联动）：**

| 差异 | 当前前端 | 应对齐 |
|------|---------|--------|
| 缺少 `data_snapshot` | 无此字段 | 补充 `data_snapshot?: string` |
| 缺少 `expires_at` | 无此字段 | 补充 `expires_at?: string` |
| `target_id` 可空 | `target_id: number`（必填） | 改为 `target_id?: number`（CREATE 时无值） |
| `group_id` 字段名 | `group_id` | 改为 `family_group_id` |
| `reviewed_at` 不存在 | `reviewed_at?: string` | 移除此字段（模型无此字段） |

### 1.2.5 authorization_action_log 模型与测试规格差异

> 测试方案 TC-11.5 要求授权码操作日志记录 `record_id`（被操作的业务记录 ID）。实际模型缺少此字段，且 `detail` 字段类型与测试规格不一致。

| 测试规格字段 | 实际模型字段 | 差异说明 |
|------------|------------|----------|
| `auth_code_id` | `authorization_code_id` | 保持模型命名（完整外键名） |
| `grantee_user_id` (FK → users) | **无此字段** | **需新增**（记录操作者身份，需求文档 line 657 定义；与 `authorization_code.grantee_user_id` 联动） |
| `record_id` (INTEGER) | **无此字段** | **需新增**（直接关联被操作记录，如 `gb_record.id`，便于查询协助人操作了哪些记录） |
| `detail` (JSONB) | `detail` (Text) | SQLite 不支持 JSONB，用 Text 存 JSON 字符串；应用层序列化 |
| 无 | `operator_name` VARCHAR(50) | 模型额外包含（与 `operation_log` 模式一致） |
| 无 | `client_id` VARCHAR(50) | 模型额外包含（标识操作来源终端） |

> **前端需新增 `AuthorizationActionLog` 类型定义**（当前 `types/index.ts` 中不存在）：

> ```typescript

>   authorization_code_id: number
>   grantee_user_id?: number   // 操作者用户 ID（需新增，需求文档定义）
>   action_type: string      // 'generate' | 'bind' | 'revoke' | 'record_create' | 'record_update' | 'record_check'
>   operator_name?: string
>   client_id?: string
>   record_id?: number       // 被操作的业务记录 ID（可选）

## 二、实施原则

### 2.1 核心原则

1. **架构先行** — 同步协议和数据格式在设计阶段确定，避免后期重构
2. **隐私优先** — `is_private` 字段在数据导入前应用，确保历史数据正确分类
3. **导入导出联动** — 模板设计和导出格式同步开发，保证字段一致性
4. **渐进增强** — 普通安全模式优先实现，增强安全模式作为可选升级
5. **测试驱动** — 每个功能模块包含单元测试和集成测试
6. **模型复用** — 后端已建模的表（family_group、pending_approval、notification 等）直接开发 API，不重复建模

### 2.2 技术约束

- **前端：** React 19.3+ + TypeScript 7.0 (strict) + Vite 8 + TanStack Router 1.x + TanStack Query 5 + Dexie.js 4 + Zustand 5 + SheetJS + ECharts 5 + Tailwind CSS 4.x
- **后端：** Python 3.14 + FastAPI 0.141+ + SQLAlchemy 2.0 (async) + Pydantic v2 + Alembic 1.20+ + PostgreSQL 17
- **认证：** PyJWT 3 (HS256) + Argon2 (passlib)
- **实时：** websockets 17+（礼簿协作 WebSocket）
- **加密：** cryptography (AES-256 服务端) + Web Crypto API (AES-256-GCM 客户端)
- **包管理：** pnpm 12+ (前端) + uv 0.12+ (后端)
- **部署：** Docker Compose（db + api + web + nginx）

**同步协议设计要点：**

```text
同步策略：混合方案
├── 现场协作（礼簿收礼）：WebSocket 实时推送（<5s 可见）
│   └── 已有 useGuestbookWebSocket hook 基础
└── 家庭共享（日常记录/人员）：HTTP 增量同步 + 5 分钟轮询
    └── 基于 sync_version 增量拉取
```

```typescript
// 增量同步请求
interface SyncPullRequest {
  client_id: string
  tables: {
    daily_records: { since_version: number }
    persons: { since_version: number }
    gb_records: { since_version: number }
  }
}

// 增量同步响应
interface SyncPullResponse {
  changes: {
    daily_records: SyncDelta<DailyRecord>
    persons: SyncDelta<Person>
    gb_records: SyncDelta<GbRecord>
  }
  server_version: number
}

interface SyncDelta<T> {
  created: T[]
  updated: T[]
  deleted: { id: number; uuid: string }[]
}

// 本地推送（离线恢复后）
interface SyncPushRequest {
  changes: {
    daily_records: SyncableDailyRecord[]
    persons: SyncablePerson[]
    gb_records: SyncableGbRecord[]
  }
}

interface SyncPushResponse {
  accepted: { table: string; id: number; uuid: string }[]
  conflicts: Conflict[]
}

interface Conflict {
  table: string
  local: Record<string, unknown>
  remote: Record<string, unknown>
  conflict_type: 'update_update' | 'update_delete' | 'create_create'
}
```

**冲突解决策略：**

| 冲突类型 | 策略 | 说明 |
|----------|------|------|
| update_update | 人工确认 | 展示本地/远程两个版本，用户选择 |
| update_delete | 人工确认 | 展示被删除记录和修改后记录，用户选择恢复或确认删除 |
| create_create | 保留两条 | UUID 不同视为不同记录，由用户后续合并 |

**Dexie.js schema 升级（v1 → v2）：**

```typescript
// 当前 v1 schema
this.version(1).stores({
  gbRecords: '++id, guestbook_id, uuid, guest_name, record_time, _syncedAt, _pendingSync',
  dailyRecords: '++id, uuid, person_id, type, event_date, _syncedAt, _pendingSync',
  persons: '++id, name, phone, relation_tag, _syncedAt, _pendingSync',
})

// 升级 v2 schema（新增同步必需字段）
this.version(2).stores({
  gbRecords: '++id, guestbook_id, uuid, guest_name, record_time, _syncedAt, _pendingSync, _updatedAt, _deleted',
  dailyRecords: '++id, uuid, person_id, type, event_date, _syncedAt, _pendingSync, _updatedAt, _deleted',
  persons: '++id, uuid, name, phone, relation_tag, _syncedAt, _pendingSync, _updatedAt, _deleted',
})
  .upgrade(tx => {
    // 为现有记录补充 uuid 和 _updatedAt
    tx.table('gbRecords').toCollection().modify(r => {
      if (!r.uuid) r.uuid = crypto.randomUUID()
      r._updatedAt = Date.now()
      r._deleted = false
    })
    // ... 同理 dailyRecords, persons
  })
```

## 四、关键技术决策

### 4.1 同步架构

**决策：混合方案（已在需求文档中确认）**

| 场景 | 方案 | 实时性 | 实现 |
|------|------|--------|------|
| 礼簿现场收礼（多终端） | WebSocket 实时推送 | <5s | `useGuestbookWebSocket` hook（已有基础） |
| 家庭云端同步（日常记录/人员） | HTTP 增量同步 + 5 分钟轮询 | ~5min | 基于 `sync_version` 增量拉取 |
| 离线恢复后 | HTTP 批量推送 | 即时 | Dexie `_pendingSync` 队列批量上传 |

**理由：**
- 现场收礼需要实时性，WebSocket 已在需求中指定
- 家庭同步不需要毫秒级实时，HTTP 轮询实现简单且服务器压力小
- 离线队列保证断网时不丢失数据

### 4.2 冲突解决策略

**策略：最终一致性 + 人工确认**

1. **检测**：比较 `sync_version` + `_updatedAt` 时间戳
2. **分类**：update_update / update_delete / create_create 三种冲突类型
3. **处理**：
   - update_update → 人工选择版本
   - update_delete → 人工选择恢复或确认删除
   - create_create → UUID 不同视为不同记录，保留两条
4. **追踪**：操作日志记录冲突解决过程（`action_type='CONFLICT_RESOLVE'`）

### 4.3 IndexedDB 存储限制应对

| 限制 | 应对策略 |
|------|----------|
| 浏览器配额（通常 10%-20% 磁盘） | 监控使用量，超 80% 时提示用户同步并清理 |
| 单表记录数（百万级可行但性能下降） | 已同步记录定期清理本地副本，保留最近 3 个月 |
| 并发写入 | Dexie 事务保证原子性，配合 `_pendingSync` 队列串行化 |

### 4.4 加密方案

**普通安全模式：**
- 传输层：TLS 1.3
- 静态加密：服务端加密（`cryptography` 库，服务端管理密钥）
- 隐私记录：服务端 `is_private` 字段权限隔离

**增强安全模式：**
- 传输层：TLS 1.3
- 静态加密：客户端 AES-256-GCM（Web Crypto API，用户密钥）
- 密钥存储：IndexedDB（`crypto.subtle` 生成的 `CryptoKey`，`extractable=false`）
- 隐私记录：客户端加密 + 服务端 `is_private` 权限隔离（双重保护）
- 家庭共享：密钥分层分发（家庭主密钥 + 成员个人密钥加密）

### 4.5 定时任务方案

**选择：APScheduler（内置于 FastAPI 进程）**

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| APScheduler | 无需额外服务，部署简单 | 单进程限制 | ✅ 选用 |
| Celery + Redis | 分布式，可扩展 | 额外服务依赖 | ❌ 过重 |
| 外部 cron | 简单 | 与 Python 进程分离 | ❌ 不灵活 |

**定时任务列表：**
- 审批过期扫描：每天 00:00 执行，标记 30 天未处理记录为 `expired`
- 软删除物理清除：每天 01:00 执行，清除 30 天前标记删除的记录
- 备份提醒检查：每天 09:00 执行，检查用户是否 7 天未备份
- 已读通知归档：每天 02:00 执行，将 30 天前已读通知的 `is_archived` 设为 true（需先通过 Alembic 新增此字段），未读通知永久保留

### 6.1 高风险项

| 风险 | 影响 | 概率 | 缓解措施 |

## 十一、附录

### 11.1 术语表

| 术语 | 定义 |
|------|------|
| **本地优先 (Local-first)** | 数据默认存储在本地 IndexedDB，服务端作为备份和共享源 |
| **增量同步** | 基于 `sync_version` 仅同步变更，而非全量数据 |
| **零知识加密** | 服务端无法解密用户数据，密钥仅存储在用户设备 |
| **隐私记录** | `is_private=true` 的记录，同步云端但仅本人可见，家人不可见 |
| **助记词** | 12/24 词（BIP-39）密钥恢复短语，用于新设备恢复 |
| **家庭主密钥** | 家庭组共享加密密钥，用每个成员个人密钥加密后分发 |
| **待审批队列** | `pending_approval` 表，家人提交的修改需主账户审批后生效 |
| **同步版本** | `sync_version` 字段，每次修改递增，用于增量同步和冲突检测 |
| **Dexie schema** | IndexedDB 表结构版本管理，通过 `version().stores()` + `upgrade()` 迁移 |
