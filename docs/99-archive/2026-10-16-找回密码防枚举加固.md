## 一、会话内容摘要

1. **超管密码查询**：礼尚云无预置超级用户密码——`super_admin` 是首个注册用户的角色，密码由注册者设定且只存哈希。本地开发库唯一超管为 `laolan_super`。
2. **密码重置 + 清锁定**：按用户要求将 `laolan_super` 密码重置为 `test123`。登录防爆破锁定是内存实现（`app/core/rate_limit.py`），当时 8001 无进程在跑，状态随旧进程退出已消失。临时拉起 uvicorn 验证登录成功（返回 super_admin token）后停止。
3. **登录失败排查**：用户报 `test123` 仍登不上且出现 3 分钟锁定。排查发现是**输错了用户名**——用昵称 `laolan` 而非用户名 `laolan_super` 登录，返回「用户名或密码错误」，连续失败触发滑动窗口锁定。经 80 端口（nginx→api 容器）直接 curl 验证新密码可用。教训：**登录用 username，不是 nickname**。
4. **Kimi Work / Kimi Code 选型讨论**：结论——本机环境操作、排查、数据修复、文档纪律 → Kimi Work；大规模代码开发与测试反馈循环 → Kimi Code；两者搭配。
5. **找回密码安全咨询**：用户观察到"用户名不存在时输入邮箱仍能发验证码"。分析确认：找回流程以**邮箱为身份凭证**（`/password-reset/request` 只收 email），不校验用户名，属设计使然；未注册邮箱返回模糊文案防枚举，符合 OWASP。真正问题在 `/password-reset/email-hint`：用户不存在返回 **404**，状态码层面泄露用户名存在性，且该端点**没有限流**（可绕过登录防爆破枚举用户名）。
6. **实施加固**（用户批准，两条）：
   - email-hint 不存在/未绑定邮箱 → **200 + `masked_email: null`**，与成功响应同构；
   - 新增 `email_hint_attempts` 限流实例，**按客户端 IP** 为键（枚举攻击轮换用户名，按用户名限流无效），复用登录防爆破参数（10 分钟 5 次，超出 429）；
   - 前端 `PasswordResetPage` / `api-client.ts` 兼容 null 响应。

## 二、关键决策与结论

- 找回密码以邮箱/手机为凭证、不依赖用户名——"用户名输错仍能收到验证码"不是漏洞，勿改。
- 防枚举统一文案保留；用户名正确性反馈通过掩码邮箱（存在才显示）传达，安全与体验兼得。
- email-hint 限流必须按 **IP** 不按用户名（攻击面是批量轮换用户名）。
- 测试打桩时间时，凡 `created_at` 由 DB/模型默认值按真实时间落库的字段，打桩偏移必须留请求耗时余量。
