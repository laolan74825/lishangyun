## 一、项目概述

### 1.1 背景

在中国社会交往中，"随礼"是一种普遍的社交习俗。无论是婚丧嫁娶、生儿育女、乔迁新居还是长辈祝寿，人们往往需要通过礼金表达心意。随礼场景可分为两类：

- **日常人情**：自己参加他人宴请时送出礼金，需要记账以便日后回礼参考。
- **宴请收礼**：自己举办宴席时接收宾客礼金，涉及多收银人员、多收款渠道、现场多人同时记账，对账目安全和数据一致性要求极高。

现有纸质礼簿或简单记账工具难以满足现场多客户端协作、账目审计追溯、多渠道收款对账等复杂场景。

### 1.2 目标

打造一款**轻量、易用、私密、安全**的礼金记账工具，覆盖完整的随礼生命周期：

- **多账户独立**：系统支持注册任意多个账户，每个账户独立运作，数据完全隔离，可灵活邀请协作。
- **日常模式**：清晰记录送出/收到的每一次礼金，掌握往来差额，提醒回礼时机。
- **礼簿模式**：宴请现场快速创建独立礼簿，支持多客户端同时收礼记账，确保账目安全可追溯。
- **合并归档**：礼簿收尾后通过合并向导建立人员关联，计算往来差额，礼簿长期保留可按宴请查看。

### 1.3 账户模型

系统支持注册任意多个账户，每个账户是独立的操作单元，拥有完整的数据所有权。账户之间完全隔离，但可以通过邀请机制灵活协作：

- **独立注册**：任何人均可注册账户，注册后即可独立使用全部记账功能
- **数据隔离**：每个账户拥有独立的人员库、记账本、日常记录、收款账户等，互不干扰
- **家庭组邀请**：任何账户均可创建家庭组并邀请其他账户加入，也可接受邀请成为其他家庭组的成员
- **协助收礼**：任何账户均可邀请其他已注册账户协助其礼簿收礼，被邀请账户在授权范围内登记和核对记录
- **多重身份**：同一账户可同时是某家庭组的主账户、另一家庭组的成员、以及多个礼簿的协助收礼人

**账户关系模型：**

```text
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│  账户 A   │  │  账户 B   │  │  账户 C   │  │  账户 D   │
│ (独立数据) │  │ (独立数据) │  │ (独立数据) │  │ (独立数据) │
└──┬──┬──┬──┘  └──┬──┬─────┘  └──┬───────┘  └──────────┘
   │  │  │        │  │            │
   │  │  │        │  │            │  协助收礼
   │  │  │        │  └────────────┼──────────────┐
   │  │  │        │  家庭组成员    │              │
   │  │  │        │               │              │
   │  │  └────────┼─── 家庭组 X ──┘              │
   │  │           │   (A 创建，B、C 加入)         │
   │  │           │                              │
   │  └───────────┼─── 家庭组 Y ─────────────────┘
   │              │   (D 创建，A 加入)
   │              │
   │              └──── 协助收礼 ──→ A 的礼簿
   │
   └──── 协助收礼 ──→ D 的礼簿

说明：
  · 每个账户拥有完全独立的数据空间（人员、记录、礼簿、账户）
  · 账户可创建/加入多个家庭组，实现数据共享
  · 账户可被邀请协助多个礼簿的收礼工作
  · 以上身份可自由组合，互不影响
```

### 1.4 目标用户

- 已成家的中青年（主要承担家庭社交往来）
- 举办婚礼、寿宴、满月酒等宴席的主人家
- 需要在现场多人协作记账的场景（酒店、家中等）
- 重视人情往来账目准确性和安全性的用户

| F-1.1 | 新增记录 | P0 | 支持「送出去」与「收进来」两种类型 |
| F-1.2 | 编辑记录 | P0 | 允许修改金额、日期、事由、收款方式等字段 |
| F-1.3 | 删除记录 | P0 | 软删除或二次确认后硬删除，删除记入日志 |
| F-1.4 | 记录列表 | P0 | 按时间倒序展示，支持筛选与搜索 |
| F-1.5 | 收款方式标记 | P1 | 日常收礼记录可标注收款方式（现金/微信/其他） |
| F-1.6 | 人员查找与新建 | P0 | 记一笔时姓名输入框从人员库联想搜索（姓名/称谓/别名/电话），选中即关联 person_id 并回填电话；人员库无此姓名时保存自动新建人员档案；人员库中有多位同名人员时弹重名提醒，由用户选择已有人员或确认新建 |

**记录字段设计（日常模式）：**

| 字段 | 必填 | 说明 |
| ------ | ------ | ------ |
| 类型 | 是 | 送出去 / 收进来 |
| 金额 | 是 | 正整数，单位分（前端展示时转换为元，如 10000 分 = ¥100.00） |
| 对方姓名 | 是 | 支持从人员库选择或新建 |
| 电话号码 | 否 | 对方手机号码，用于精确匹配与联系 |
| 事由/事件 | 是 | 自由文本（最多 30 字），如"小孙子满月"；前端提供婚礼/满月酒/周岁宴/生日/寿宴/乔迁/升学宴/丧葬/节日红包等常用事由联想，礼簿事由仍为枚举 |
| 收款方式 | 否 | 收进来时可选：现金、微信、其他 |
| 收款账户 | 否 | 关联具体微信账户或现金收银人（对应数据模型 account_id 字段） |
| 日期 | 是 | 事件日期，默认今天 |
| 备注 | 否 | 自由文本 |
| 创建/更新时间 | 自动 | 系统自动记录 |
| 记账人员 | 自动 | 当前操作者标识 |

**金额验证规则：**

- 最小金额：100 分（¥1.00），低于此值提示"金额不能小于 1 元"
- 单笔最大：10000000 分（¥100,000.00），超过此值提示"单笔金额不能超过 10 万元"
- 礼簿总额：无硬性上限，但微信收款受每日限额约束（见 payment_account.daily_limit）
- 现金收款：无独立限额，但单笔超过 5000000 分（¥50,000）时二次确认
- 校验失败时，前端红色高亮金额输入框并显示对应错误信息，不提交至后端

### 2.3 模块二：礼簿管理与现场收礼（核心模块）

> **礼簿（Guest Book）**是独立于日常记录的长期事件记录，用于某一次具体宴席的现场收礼场景。礼簿经历「收礼中 → 收尾中 → 已归档」三个阶段，收礼记录始终保留在礼簿中，可通过合并向导建立与人员库的关联。宴席结束后仍可补录。
>
> **收礼模块是本系统的核心场景**，涉及现场多人协作、多账户收款、账目安全等高复杂度需求，必须在产品设计中优先保障稳定性与易用性。

#### 2.3.1 礼簿生命周期

礼簿为长期保留的事件记录，经历三个阶段：

| 状态 | 含义 | 可用操作 | 协作支持 |
| ------ | ------ | ---------- | ---------- |
| **收礼中**（active） | 宴席进行中，现场多人协作收礼 | 收礼记账、对账、多端同步、终端设置 | 支持多端协作 |
| **收尾中**（closing） | 宴席结束，进入补录与修正阶段 | 补录宾客、修正记录、最终对账、合并向导、按宴请查看 | 仅单端操作 |
| **已归档**（archived） | 用户确认数据无误，锁定为只读 | 查看礼簿详情、按宴请查看、导出 | 不可操作 |

**状态流转：**

```text
收礼中 ──→ 收尾中 ──→ 已归档
  │           │
  │  用户确认  │  用户确认
  │  结束宴席  │  数据无误
  │           │
  └───────────┘
   合并向导自动弹出
   用户可选择执行或跳过
```

> 所有状态转换完全由用户手动控制，不设自动过期或自动归档机制。

**状态转换矩阵：**

| 当前状态 | 目标状态 | 是否允许 | 前置条件 | 可逆性 |
| ---------- | ---------- | ---------- | ---------- | -------- |
| 收礼中 | 收尾中 | ✅ 允许 | 用户点击"结束宴席"按钮，二次确认 | 可逆（可返回收礼中） |
| 收尾中 | 已归档 | ✅ 允许 | 用户点击"确认归档"按钮，二次确认；建议但非强制：所有记录已对账 | 可逆（可恢复为收尾中） |
| 收尾中 | 收礼中 | ✅ 允许 | 用户点击"恢复收礼"按钮，二次确认 | 可逆 |
| 已归档 | 收尾中 | ✅ 允许 | 用户点击"恢复收尾中"按钮，二次确认；恢复后可补录/修正，确认无误后重新归档 | 可逆（可重新归档） |
| 已归档 | 收礼中 | ❌ 禁止 | 必须先恢复为收尾中，再由收尾中返回收礼中 | — |
| 收礼中 | 已归档 | ❌ 禁止 | 必须经过收尾中阶段 | — |

**转换说明：**

- **收礼中 → 收尾中**：宴席结束，进入补录和修正阶段。此转换可逆，用户可恢复收礼中状态继续记账。
- **收尾中 → 已归档**：用户确认数据无误后锁定。**前置建议**：系统检查是否存在未对账记录（check_status=unchecked），若有则提示"仍有 X 条记录未对账，建议先完成对账再归档"，但用户可选择跳过直接归档。
- **已归档 → 收尾中**：发现归档后的数据有误时，可恢复为收尾中进行补录和修正，确认无误后重新归档；归档时间清空，重新归档时重新记录。已归档数据在恢复前仍为只读。
- **删除语义**：已归档礼簿可删除（F-2.5），删除前需二次确认，删除后数据不可恢复（软删除，30 天后物理清除）。

| 编号 | 功能点 | 优先级 | 说明 |
| ------ | -------- | -------- | ------ |
| F-2.1 | 新建礼簿 | P0 | 填写礼簿名称、事由类型、宴席日期，创建独立礼簿，自动进入「收礼中」状态。**收款账户前置检查**：若系统未设置任何收银员和微信账户，弹窗引导前往「账户管理」设置（可返回礼簿列表），设置完成前不可进入表单；已设置则进入表单，收银员/微信账户默认「系统默认」（跟随系统当前激活账户），可改选其他已有账户，规则详见下方「新建礼簿的收款账户规则」 |
| F-2.2 | 结束宴席（进入收尾） | P0 | 用户确认宴席结束，礼簿进入「收尾中」状态。关闭多端协作会话，自动弹出合并向导 |
| F-2.3 | 暂停/恢复礼簿 | P1 | 宴席间隙可暂停本终端的收礼操作，防止误操作（仅收礼中状态可用）。**暂停为终端级 UI 锁定**，非独立数据状态：锁定本终端收礼界面（显示遮罩层，需记账员姓名解锁），不影响其他终端正常操作；不改变礼簿 status 字段，不涉及协作会话状态变更 |
| F-2.4 | 归档礼簿 | P0 | 用户确认所有数据无误后，手动将礼簿标记为「已归档」，锁定为只读不可修改；**已归档可恢复为收尾中**（见状态转换矩阵），恢复后可补录/修正并重新归档 |
| F-2.5 | 删除礼簿 | P1 | 仅空礼簿或已归档礼簿可删除；收尾中的礼簿需先归档或删除所有记录 |
| F-2.6 | 礼簿列表 | P0 | 展示所有礼簿（收礼中 / 收尾中 / 已归档），支持按状态和时间筛选 |
| F-2.7 | 礼簿详情 | P0 | 查看礼簿内所有收礼记录及汇总统计（所有状态均可查看） |
| F-2.8 | 收尾期补录 | P0 | 收尾中状态下可继续新增宾客记录（如宾客事后补礼），支持手动设置记账时间；**补录的记录无需对账，自动标记为已对账** |
| F-2.9 | 收尾期修正 | P1 | 收尾中状态下可修改已有记录（如金额错误修正），操作记入日志 |

**礼簿字段设计：**

| 字段 | 必填 | 说明 |
| ------ | ------ | ------ |
| 礼簿名称 | 是 | 如"张小明婚礼收礼" |
| 事由类型 | 是 | 婚礼、寿宴、满月酒、乔迁、升学、丧葬、其他 |
| 宴席日期 | 是 | 举办日期 |
| 创建时间 | 自动 | 系统记录 |
| 收尾时间 | 自动 | 进入收尾阶段时记录 |
| 归档时间 | 自动 | 标记归档时记录 |
| 状态 | 自动 | 收礼中 / 收尾中 / 已归档 |
| 关联主人家 | 是 | 可设置一个或多个主人家人员 |

**新建礼簿的收款账户规则：**

- **前置检查**：进入新建页面前加载系统全部收银员和微信账户（加载期间显示加载态，避免误判）。若两者均未设置，弹出引导弹窗：「去账户管理」跳转账户管理页，「返回礼簿列表」退出创建流程。仅当两者都为空时才拦截；只缺其一（如只有微信账户）不拦截。
- **默认值**：收银员和微信账户下拉框默认选中「系统默认」，即创建后跟随系统当前激活账户，不在礼簿终端设置中写死账户 ID。
- **可选项**：下拉列表包含该类型全部已有账户（含未激活账户），与账户管理页的礼簿账户设置口径一致。
- **操作员解析顺序**：提交时按「手动选择的具体收银员 → 系统默认（当前激活收银员）→ 第一个收银员账户（兜底）→ 本机记账员姓名」解析操作员姓名；四者皆空时提示「请选择收银员」并阻止提交。
- **默认设置保存**：创建成功后，将所选账户（「系统默认」时为空）保存为**礼簿级默认设置**（`client_id='default'`，收礼页与账户管理页均读取该键），并记录解析出的操作员姓名；随后自动跳转收礼界面。本终端如需使用不同账户，可在终端设置页按本机标识单独覆盖。

#### 2.3.2 终端记账员设置

> 每个终端（客户端）在加入礼簿协作后，必须先设置一名记账员（操作者），该身份将用于操作日志记录。同时，每个终端需分别设置现金和微信的默认收款人，收礼时自动带出，可随时切换或重新设置。

| 编号 | 功能点 | 优先级 | 说明 |
| ------ | -------- | -------- | ------ |
| F-2.10 | 终端记账员设置 | P0 | 每个终端首次进入收礼界面前，必须设置一名记账员姓名/昵称，用于操作日志标识 |
| F-2.11 | 终端默认现金收银人设置 | P0 | 每个终端可独立设置默认现金收银人，收礼时自动带出 |
| F-2.12 | 终端默认微信账户设置 | P0 | 每个终端可独立设置默认微信收款账户，收礼时自动带出 |
| F-2.13 | 收款人临时切换 | P0 | 收礼过程中可随时切换为其他现金收银人或微信账户 |

**微信限额预警规则：**

- 每个微信收款账户可设置「每日限额金额」（默认**20000000分，即¥200,000**）
- 系统实时计算该账户在礼簿当日已收金额
- 剩余可用额度 = 每日限额 - 当日已收金额
- 当剩余可用额度 **< 200000分（¥2000）**时：
  - 在收款账户选择列表中，该账户项**文字标红/标黄**，并显示"剩余 ¥X,XXX"
  - 提示记账人"该账户剩余额度紧张，注意切换"
- 当剩余可用额度 **≤ 20000分（¥200）**时：
  - 该账户在选择列表中**置灰禁用**，不可选择
  - 提示"该账户剩余额度不足，请切换其他账户"
- 当录入金额**超出**该账户剩余可用额度时：
  - **禁止保存**该条记录
  - 弹出警告提示："录入金额 ¥X,XXX 超出该账户剩余额度 ¥X,XXX，请切换账户或调整金额"

### 2.5 模块四：多客户端同步

> 本模块聚焦**宴席现场协作**场景：多位亲友用各自设备同时录入同一礼簿，数据实时同步。家庭数据共享（日常记录云同步、家人协作审批）见模块十一。

| 编号 | 功能点 | 优先级 | 说明 |
| ------ | -------- | -------- | ------ |
| F-4.1 | 创建协作会话 | P0 | 礼簿创建者生成一个协作码或二维码，供其他客户端加入。**协作码有效期 24 小时**，过期后需重新生成；每个礼簿同时最多支持 10 个客户端并发连接 |
| F-4.2 | 加入协作会话 | P0 | 其他客户端输入协作码或扫描二维码加入礼簿 |
| F-4.3 | 终端记账员绑定 | P0 | 加入后必须设置本终端记账员姓名，设置后才可开始记账 |
| F-4.4 | 实时数据同步 | P0 | 任一客户端新增记录后，其他在线客户端5秒内可见 |
| F-4.5 | 离线暂存 | P1 | 网络中断时本地暂存，恢复后自动同步 |
| F-4.6 | 冲突检测与解决 | P1 | 同名同金额记录自动标记待确认；操作员可手动标记/解标记 |
| F-4.7 | 同步状态提示 | P1 | 界面显示当前同步状态：已同步/同步中/离线 |
| F-4.8 | 退出协作 | P1 | 客户端可主动退出，退出后不再接收同步数据；**终端设置保留**，同一 client_id 重新加入时自动恢复 |
| F-4.9 | 会话关闭与清理 | P2 | 礼簿进入收尾中状态时自动关闭协作会话（拒绝新连接，现有连接可完成当前操作后断开）；**会话数据在礼簿进入已归档状态后 7 天自动清理**（清理 WebSocket 会话缓存、临时同步队列，不影响已持久化的业务数据） |

**同步策略：**

- 采用**最终一致性**模型，以时间戳+客户端标识为冲突仲裁依据
- 每笔记录携带全局唯一ID（UUID），从根本上避免重复写入
- 网络恢复后按时间顺序重放离线队列

**离线冲突解决策略：**

| 操作类型 | 冲突场景 | 解决策略 | 说明 |
| ---------- | ---------- | ---------- | ------ |
| 创建 | 两客户端同时创建相同 UUID 的记录 | **拒绝重复** | UUID 唯一约束，后到的写入被拒绝，客户端收到冲突提示后丢弃本地副本 |
| 更新 | 两客户端修改同一记录的不同字段 | **Last-Write-Wins** | 以 `sync_version` 较大者为准，后到的写入覆盖先到的；因字段独立，通常不丢失数据 |
| 更新 | 两客户端修改同一记录的相同字段 | **Last-Write-Wins + 冲突标记** | 以 `sync_version` 较大者为准，但系统将该记录标记为 `conflicted=true`，前端显示"数据冲突，请核实"提示，操作员可手动查看历史版本并修正 |
| 删除 | 一客户端更新，另一客户端删除同一记录 | **删除优先** | 删除操作优先执行，更新操作被丢弃；删除操作记入 operation_log |

**sync_version 比较逻辑：**

- 每次修改记录时，`sync_version` 递增 1
- 同步时比较两端 `sync_version`，较大者为最新版本
- 若 `sync_version` 相同，比较 `updated_at` 时间戳，较新者为准
- 若时间戳也相同（极小概率），以服务端接收顺序为准

**冲突标记 UI 呈现：**

- 冲突记录在列表中以橙色高亮显示
- 详情页顶部显示"此记录存在冲突修改，请核实"警告条
- 提供"查看历史版本"按钮，展示 before_data 和 after_data 对比
- 操作员修正后点击"确认解决"，清除 `conflicted` 标记

**两种同步模式对比：**

| 维度 | 现场协作同步（本模块） | 家庭云端同步（模块十一） |
| ------ | ---------------------- | ------------------------ |
| 场景 | 宴席现场多人同时记账 | 家人日常数据共享 |
| 传输协议 | WebSocket (wss) 实时推送 | HTTPS 增量同步 + 定时轮询 |
| 数据范围 | 单个礼簿的 gb_records | 全量数据（日常记录 + 礼簿 + 人员） |
| 生命周期 | 临时会话，宴席结束后关闭 | 长期持续，家庭组存续期间有效 |
| 冲突处理 | 自动标记待人工确认 | 主账户审批机制 |
| 离线策略 | 本地暂存，恢复后重放 | IndexedDB 为主，上线后增量上传 |

### 2.8 模块七：对账管理

> 宴席中途，**收银员（现金/微信）与记账人之间需要随时进行实时对账**，以便及时发现和纠正错记、漏记、多记。对账不是一次性收尾动作，而是贯穿收礼全过程的持续核对机制。对账是协作团队内部的账目核对。

#### 2.8.1 对账角色与流程

| 编号 | 功能点 | 优先级 | 说明 |
| ------ | -------- | -------- | ------ |
| F-7.1 | 对账视图入口 | P0 | 礼簿详情页提供「对账」Tab，收银员与记账人可在此核对；**收礼界面也提供对账快捷入口**，无需切换页面即可发起对账 |
| F-7.2 | 按收银员筛选 | P0 | 收银员可筛选查看自己经手的所有记录（现金/微信） |
| F-7.3 | 按记账员筛选 | P1 | 可按记账员筛选，查看某记账人录入的记录 |
| F-7.4 | 记录对账状态 | P0 | 每条收礼记录有「对账状态」：未对账（默认）/ 已对账 |
| F-7.5 | 批量标记已对账 | P0 | 收银员核对无误后，批量勾选记录一键标记为"已对账" |
| F-7.6 | 单条标记已对账 | P0 | 点击单条记录旁的对账按钮标记为"已对账" |
| F-7.7 | 已对账记录过滤 | P1 | 对账视图默认显示全部，可筛选"仅未对账"、"仅已对账" |
| F-7.8 | 取消已对账标记 | P1 | 已标记为"已对账"的记录，可随时取消标记，恢复为"未对账"重新对账 |
| F-7.9 | 对账进度统计 | P0 | 顶部显示对账进度：已对账 X 笔 / 总 Y 笔，金额已对账 ¥A / 总 ¥B |
| F-7.10 | 对账差异标记 | P1 | 收银员发现某笔记录金额与实收不符时，可标记"待核实" |
| F-7.11 | 未对账数量提示 | P1 | 收礼界面常驻显示当前未对账记录数量；未对账超过 20 笔时**额外显示一条对账建议**，提示操作者可前往对账，但**不弹窗、不阻断操作** |

**对账管理规则：**

- 对账发生在**收银员与记账人之间**，是协作团队内部核对机制
- **对账贯穿收礼全过程**，不局限于宴席结束后；收银员可在任意时刻与记账人核对当前账面与实收
- 新录入的记录默认状态为「未对账」
- 收银员（现金收银人或微信收款人）清点实收金额后，与记账人录入的账面金额核对
- 核对无误后标记为「已对账」
- 「已对账」记录在对账视图中显示绿色对勾标识
- 已对账记录不再出现在"仅未对账"筛选结果中
- 取消已对账标记后，记录恢复为「未对账」状态，可重新对账
- 发现漏记时，记账人可补记（支持手动设置记账时间，精确到秒）

**对账场景示例：**

```text
张三（现金收银员）在宴席中途清点手中现金：
- 打开「对账」Tab → 筛选「现金-张三」
- 看到记账人已录入32笔，账面金额¥15,200
- 张三实际清点现金也是¥15,200，核对无误
- 批量勾选全部32笔 → 点击「标记为已对账」
- 已对账记录显示绿色对勾
```

### 2.9 模块八：礼簿合并与智能推荐

> 礼簿进入收尾阶段后，系统自动弹出合并向导，引导用户将礼簿中的宾客与人员库建立关联。合并操作不搬迁数据——收礼记录始终保留在礼簿中，仅建立人员映射关系，使人员详情页可计算包含该礼簿在内的完整往来差额。

| 编号 | 功能点 | 优先级 | 说明 |
| ------ | -------- | -------- | ------ |
| F-8.1 | 自动弹出合并向导 | P0 | 礼簿进入收尾中状态时自动弹出合并向导，用户可选择立即执行或稍后手动发起 |
| F-8.2 | 人员匹配推荐 | P0 | 对礼簿中的每位宾客，从历史人员库中智能推荐可能的匹配项 |
| F-8.3 | 电话+姓名精确匹配 | P0 | **电话号码相同且姓名（含同音字）匹配的记录，视为精确匹配**，直接关联 |
| F-8.4 | 已匹配人员跳过 | P0 | 已确认匹配过的人员不再重复推荐，直接沿用上次确认的映射关系 |
| F-8.5 | 推荐确认机制 | P0 | 所有推荐匹配（包括同名、同音字、别名等）必须由用户手动确认 |
| F-8.6 | 推荐规则 | P0 | 基于姓名相似度（同音字、别名）、历史往来记录匹配 |
| F-8.7 | 手动确认/新建 | P0 | 用户确认推荐匹配或选择「新建人员」 |
| F-8.8 | 批量确认 | P1 | 对高置信度匹配项支持一键批量确认 |
| F-8.9 | 合并预览 | P1 | 合并前预览所有映射关系及合并后的人员关联变化 |
| F-8.10 | 合并执行 | P0 | 确认后将礼簿记录的 person_id 关联到匹配的人员，不搬迁数据，记录始终留在礼簿中 |
| F-8.11 | 合并后宴请关联 | P0 | 合并完成后，该礼簿中已关联人员的记录自动纳入人员详情页的「按宴请查看」列表（详见 F-9.7） |
| F-8.12 | 撤销合并 | P2 | 合并后 **7 天内**可撤销，清除 person_id 关联关系 |
| F-8.13 | 收尾中/已归档可合并 | P0 | 合并向导对收尾中、已归档状态的礼簿开放；收礼中的礼簿禁止合并（宾客与金额仍在变动，须先结束宴席进入收尾） |
| F-8.14 | 已合并礼簿修改自动同步 | P0 | 已合并礼簿（person_merged_at 非空）中修改宾客姓名/电话的记录，保存时自动按最新姓名/电话重新解析 person_id；未合并礼簿不受影响 |
| F-8.15 | 已合并礼簿补录自动合并 | P0 | 已合并礼簿中通过单条补录、批量导入、协作代录创建的记录，创建时自动解析 person_id 并关联人员库 |
| F-8.16 | 无法匹配记录确认新建人员 | P0 | 合并向导将无法匹配的记录以列表展示，用户勾选确认后按礼簿数据（姓名、电话）新建人员并自动关联；服务端创建前先按匹配规则查重，人员已存在（同名同电话可精确匹配）时直接关联而不重复建人 |

**智能推荐匹配算法（简要规则）：**

1. **电话+姓名精确匹配**：电话号码相同且姓名（含同音字）匹配 → 自动匹配，不再显示推荐列表
2. **精确匹配**：姓名完全一致 → 置信度 100%，但仍需用户确认
3. **同音字匹配**：姓名拼音相同（如"张峰"↔"张锋"）→ 置信度 85%
4. **历史别名匹配**：该姓名曾出现在历史记录的备注/昵称中 → 置信度 75%
5. **部分匹配**：包含关系（如"张小明"↔"小明"）→ 置信度 60%
6. **无匹配**：历史库中无相关记录 → 推荐「新建人员」

| F-11.19 | 加密数据导出 | P2 | 增强安全模式下，导出数据文件使用用户密钥加密（AES-256-GCM），导出文件为加密格式，需密钥才能打开；普通安全模式下导出为标准 Excel/CSV |
| F-11.20 | 通知系统 | P1 | 应用内消息通知：审批通过/拒绝/过期、家人加入家庭组、合并向导建议等事件触发通知；通知铃铛角标显示未读数，点击跳转到关联实体详情；详见「通知系统规格」章节 |

**双安全模式说明：**

| 维度 | 普通安全（默认） | 增强安全（可选） |
| ------ | ------------------ | ------------------ |
| 传输加密 | TLS 1.3 | TLS 1.3 |
| 静态加密 | 服务端加密（服务端管理密钥） | 客户端 AES-256-GCM 加密（用户密钥，服务端零知识） |
| 隐私记录 | 服务端权限隔离 | 客户端加密 + 服务端权限隔离（双重保护） |
| 家庭共享 | 服务端权限隔离，家人可查看非隐私数据 | 密钥分层分发，家人解密后可查看非隐私数据 |
| 用户摩擦 | 零（开箱即用） | 需生成/保管密钥和助记词 |
| 数据恢复 | 服务端备份即可恢复 | 必须有助记词或密钥备份，否则无法恢复 |
| 适用场景 | 绝大多数用户日常使用 | 对数据隐私有极高要求的用户 |

> **设计原则**：普通安全模式面向所有用户，零摩擦开箱即用；增强安全模式面向对隐私有极高要求的用户，需主动开启。两种模式下数据均可正常备份和导出，区别仅在于加密层级和密钥管理方式。
>
> **模式切换流程**：
>
> - **普通 → 增强**：设置页选择"增强安全" → 引导生成密钥（Web Crypto API） → 显示恢复助记词，要求用户抄录并确认 → 客户端加密全部本地数据 → 上传密文至服务端 → 切换完成
> - **增强 → 普通**：设置页选择"普通安全" → 要求输入助记词或导入密钥以验证身份 → 系统解密全部云端数据 → 二次确认弹窗"切换后数据将以服务端加密存储，是否继续？" → 用户确认 → 服务端切换为普通加密 → 清除客户端密钥缓存（密钥配置记录保留但标记为 inactive，以备将来重新启用）

**数据导入模板规范：**

| 模板名称 | 包含字段 | 说明 |
|----------|----------|------|
| 日常记录模板 | 姓名、电话、类型(收/送)、金额、事由、支付方式、日期、备注 | 用于批量导入历史人情往来记录；事由可选全部 8 种枚举值 |
| 礼簿记录模板 | 礼簿名称、事由类型、宴席日期、宾客姓名、电话、金额、支付方式、收银人、记账时间、备注 | 用于导入旧礼簿数据，系统按礼簿名称自动分组；事由类型不含"节日红包"（7 种） |

**数据导入校验规则：**

| 校验项 | 规则 | 错误提示 |
| -------- | ------ | ---------- |
| 必填字段 | 姓名、金额、日期（日常）；礼簿名称、宾客姓名、金额、宴席日期（礼簿） | "第 X 行缺少必填字段：{field_name}" |
| 金额格式 | 正整数或最多两位小数，转换为分后在 [100, 10000000] 范围内 | "第 X 行金额格式错误，应为 1-100000 之间的数字" |
| 日期格式 | YYYY-MM-DD 或 YYYY/MM/DD，不晚于今天 | "第 X 行日期格式错误或超出合理范围" |
| 事由类型 | 日常记录导入：婚礼/生日/满月酒/乔迁/升学/丧葬/节日红包/其他（全部 8 种）；**礼簿记录导入：婚礼/生日/满月酒/乔迁/升学/丧葬/其他（7 种，不含节日红包——holiday 为日常专用）** | "第 X 行事由类型无效，请从下拉列表选择" |
| 支付方式 | 必须为 cash/wechat/other 之一（可选字段） | "第 X 行支付方式无效" |
| 重复检测 | 按 (姓名 + 金额 + 日期) 组合判断，与现有记录比对 | "第 X 行与现有记录重复：{existing_record_summary}" |
| 文件大小 | 单次导入不超过 10,000 行，文件大小不超过 5MB | "导入文件过大，请分批导入" |
| 编码检测 | 自动检测 UTF-8 / GBK / GB2312 编码 | "文件编码无法识别，请转换为 UTF-8 后重试" |

**导入行为：**

- **部分导入模式**：校验通过的行正常导入，校验失败的行跳过并生成错误报告
- **错误报告格式**：Excel 文件，包含原数据 + 错误列（行号、字段名、错误描述）
- **重复处理策略**：重复记录默认跳过，用户可选择"覆盖现有记录"或"全部导入（含重复）"
- **事务控制**：单次导入为单个事务，全部成功或全部回滚（用户可在预览页确认后提交）

**家庭共享架构：**

```text
┌─────────────────────────────────────────────────────┐
│                    家庭组                            │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐          │
│  │ 主账户    │  │ 家人A    │  │ 家人B    │          │
│  │ (审批权)  │  │ (读写)   │  │ (读写)   │          │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘          │
│       │              │              │                │
│       ▼              ▼              ▼                │
│  ┌──────────────────────────────────────────┐       │
│  │         云端数据池（PostgreSQL）           │       │
│  │  · 日常记录（含隐私记录，权限隔离）        │       │
│  │  · 礼簿数据（含隐私记录，权限隔离）        │       │
│  │  · 人员库（合并视图）                     │       │
│  │  · 待审批队列                             │       │
│  └──────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────┘
```

**共享权限规则：**

- **主账户**：完整读写权限 + 审批权，可邀请/移除成员，可设置记录「隐私记录」
- **家庭成员**：可查看家庭共享池中的所有非隐私数据；可提交新增和修改，但需主账户审批后才正式生效
- **「隐私记录」**：同步至云端但仅标记者本人可查看，其他家庭成员不可见；统计合计中仅本人可看到包含隐私数据的汇总

> **审批流程补充说明**：
>
> - 家人提交的修改在审批前仅存在于 pending_approval 表中，不影响家庭共享数据池
> - 审批通过后，系统根据 payload 写入对应业务表，同时通知提交人（应用内消息）
> - 审批拒绝时，主账户须填写拒绝原因，系统通知提交人
> - 待审批超过 30 天未处理的记录自动标记为 expired（已过期），需提交人重新提交
> - 主账户可在审批队列中按提交人、提交时间、记录类型筛选和排序

### 通知系统规格

系统采用应用内消息（in-app notification）机制，暂不实现推送通知或邮件通知。

**通知表结构（notification）：**

| 字段 | 类型 | 说明 |
| ------ | ------ | ------ |
| id | INTEGER PK | 自增主键 |
| recipient_id | INTEGER FK | 接收人（关联 users.id） |
| type | VARCHAR(30) | 通知类型：approval_approved / approval_rejected / approval_expired / family_member_joined / merge_suggested |
| title | VARCHAR(100) | 通知标题 |
| body | TEXT | 通知正文 |
| related_entity | VARCHAR(50) | 关联实体类型（如 pending_approval、family_group、person） |
| related_id | INTEGER | 关联实体 ID |
| is_read | BOOLEAN | 是否已读，默认 false |
| created_at | DATETIME | 创建时间 |

**通知触发事件：**

| 事件 | 接收人 | 通知内容 |
| ------ | -------- | ---------- |
| 审批通过 | 提交人 | "您的提交已通过审批，数据已同步至家庭共享" |
| 审批拒绝 | 提交人 | "您的提交已被拒绝，原因：{review_note}" |
| 待审批过期 | 提交人 | "您的提交已过期（超过30天未审批），请重新提交" |
| 家人加入家庭组 | 主账户 | "{display_name} 已加入家庭组" |
| 合并向导建议 | 礼簿创建者 | "礼簿 {name} 检测到可合并的人员，建议执行合并" |

**UI 呈现：**

- 顶部导航栏显示通知铃铛图标，未读通知数以红色角标显示
- 点击铃铛展开通知列表，按时间倒序排列，最多显示 50 条
- 点击通知项标记为已读，并跳转到关联实体详情页
- 通知保留策略：已读通知 30 天后自动归档，未读通知永久保留

**存储与检索：**

- 通知存储在服务端 PostgreSQL 数据库
- 客户端通过轮询（每 60 秒）或 WebSocket（协作会话期间）获取新通知
- 离线期间产生的通知在客户端上线后批量拉取

**增强安全模式适配：**

- 增强安全模式下，通知内容不包含敏感数据（仅标题和通用描述）
- 通知正文不加密（服务端生成，非用户数据），接收人客户端解密后展示

```text
┌──────────────────────────────────────────────────────────────┐
│                    增强安全模式                                │
│                                                              │
│  客户端A（主账户）                                            │
│  ┌────────────────────────────────────────────┐              │
│  │  个人密钥（AES-256-GCM）                    │              │
│  │  ↓ 加密                                    │              │
│  │  家庭主密钥                                 │              │
│  │  ↓ 用成员B的个人公钥加密                    │              │
│  │  加密的家庭主密钥 ──────────────────┐       │              │
│  └────────────────────────────────────────────┘              │
│                                                              │
│  客户端B（家庭成员）                                          │
│  ┌────────────────────────────────────────────┐              │
│  │  个人密钥（AES-256-GCM）                    │              │
│  │  ↓ 解密                                    │              │
│  │  家庭主密钥 ←──────────────────────┘       │              │
│  │  ↓ 解密                                    │              │
│  │  家庭共享数据（明文）                       │              │
│  └────────────────────────────────────────────┘              │
│                                                              │
│  云端（PostgreSQL）                                           │
│  ┌────────────────────────────────────────────┐              │
│  │  加密数据（密文）                           │              │
│  │  · 服务端无法解密，零知识                   │              │
│  │  · 仅持有密钥的客户端可读写明文             │              │

└──────────────────────────────────────────────────────────────┘
```

> 增强安全模式下，所有同步至云端的数据均在客户端加密后传输，服务端仅存储密文。家庭共享通过密钥分层实现：主账户生成家庭主密钥，用每位成员的个人密钥加密后分发，成员用自己的个人密钥解密获取家庭主密钥，进而解密共享数据。

## 三、非功能需求

| 编号 | 需求类别 | 需求描述 |
| ------ | ---------- | ---------- |
| NF-1 | 性能 | 冷启动 < 2秒；列表加载 < 1秒；单礼簿支持 3000+ 笔记录流畅运行 |
| NF-2 | 易用性 | 核心收礼操作（姓名+金额+方式）不超过 5 步完成；大字号界面适合现场快速录入 |
| NF-3 | 隐私安全 | **双安全模式**：①普通安全（默认）— TLS 传输 + 服务端加密（服务端管理密钥）+ 隐私记录权限隔离，零摩擦；②增强安全（可选）— 客户端 AES-256-GCM 零知识加密，密钥永不离开设备，服务端无法解密；家庭共享通过密钥分层分发实现。**本地优先架构**：日常数据默认存本地；「隐私记录」同步云端但仅本人可查看；家庭共享数据按需同步至服务端，权限隔离；礼簿现场协作采用端到端加密；协作码时效限制（如24小时）；家人修改需主账户审批 |
| NF-4 | 数据一致性 | 现场协作同步：最终一致性，冲突记录明确标记待人工确认；家庭云端同步：增量同步 + 版本向量，主账户审批确保数据质量；离线时 IndexedDB 为主存储，上线后自动增量同步 |
| NF-5 | 审计安全 | 操作日志防篡改、不可删除；关键操作（删除、合并）需二次确认 |
| NF-6 | 兼容性 | 支持**手机、平板、电脑**三类设备；响应式布局自适应屏幕宽度；平板横屏适配（现场记账常用平板）；桌面端支持主流浏览器（Chrome/Firefox/Edge/Safari），移动端支持系统浏览器及微信内置浏览器 |
| NF-7 | 离线可用 | 支持离线记账、断网续传；网络恢复后自动同步 |
| NF-8 | 轻量化 | 应用体积控制在 10MB 以内；PWA模式可安装到主屏 |

## 四、用户场景（Use Cases）

### 场景一：日常人情 — 参加婚礼后记账
>
> 用户参加表弟婚礼，随了1000元红包。酒席结束后在回家的路上打开手机，30秒内完成记录。

**关键路径：**

1. 打开应用 → 进入首页 → 点击「记一笔」
2. 选择类型「送出去」
3. 输入金额「1000」、选择对方「表弟-李明」、事由「婚礼」
4. 点击「保存」

### 场景二：宴请现场 — 创建礼簿并多人协作收礼
>
> 张小明举办婚礼，邀请了200位宾客。主人家安排3位亲友帮忙记账：张三负责现金收银，李四和赵六各用一个微信号收款（均设置每日限额¥200,000）。3人分别用自己的手机/平板加入同一个礼簿协作记账。

**关键路径：**

1. **主人家创建礼簿**
   - 打开应用 → 点击「新建礼簿」
   - 输入礼簿名称「张小明婚礼收礼」、事由「婚礼」、日期
   - 预设现金收银人「张三」「王五」、微信账户「李四-微信1」「赵六-微信2」（限额均¥200,000）
   - 生成协作二维码

2. **记账人员加入协作并设置终端**
   - 张三用自己的手机扫码加入 → 设置记账员「张三」→ 设置默认现金收银人「张三」、默认微信「李四-微信1」
   - 李四用自己的手机扫码加入 → 设置记账员「李四」→ 设置默认现金收银人「王五」、默认微信「李四-微信1」
   - 赵六用平板扫码加入 → 设置记账员「赵六」→ 设置默认现金收银人「张三」、默认微信「赵六-微信2」

3. **现场收礼记账（单笔现金，使用终端默认）**
   - 宾客上前送礼 → 张三打开收礼界面
   - 输入宾客姓名「王大壮」、电话「138****1234」、金额「500」
   - **手动选择**收款方式「现金」
   - 现金收银人**自动带出**「张三」（本终端预设）
   - 张三临时切换为王五收银 → 选择「王五」
   - 点击「提交」→ 实时同步到所有客户端 → 底部合计自动更新

4. **宾客现场核对**
   - 王大壮送完礼后，侧头看向张三的手机屏幕
   - 屏幕底部「最近收款记录」区域已更新："1. 王大壮  ¥500  12:33:45"
   - 王大壮确认无误后离开
   - 若发现错误可当场指出，张三立即编辑修正

5. **代理送礼（被代理人等级平级，统一支付方式）**
   - 赵大伟上前说"我替我们全家四口人随礼"
   - 李四打开「代理送礼」模式
   - 录入经办人「赵大伟」（可选，也可不填）
   - 添加被代理人：赵大伟、赵大伟妻子、赵大伟父亲、赵大伟同事小王
   - 分别为每人录入金额
   - 选择统一收款方式「现金」→ 收银人自动带出「王五」（李四终端预设）
   - 界面显示合计：4人，**合计¥2,400**
   - 点击「批量提交」→ 生成4条**完全独立的收礼记录**，每条等级与普通记录相同
   - 最近收款记录区域更新显示4条新记录

6. **代理送礼（分别支付方式）**
   - 钱大姐说"我替3个朋友随礼，金额不一样，有的微信有的现金"
   - 赵六在平板上操作：
     - 经办人「钱大姐」
     - 被代理人1：朋友A — 现金 — 张三收银 — ¥500
     - 被代理人2：朋友B — 微信 — 李四-微信1 — ¥800
     - 被代理人3：朋友C — 现金 — 王五收银 — ¥600
   - 合计：3人，合计¥1,900
   - 批量提交 → 生成3条独立记录

7. **现场收礼记账（微信扫码付款）**
   - 宾客说"我微信付款"
   - 李四打开收礼界面，**手动选择**收款方式「微信」
   - 微信收款账户**自动带出**「李四-微信1」（李四终端预设的默认微信）
   - 界面下方**自动显示李四-微信1的收款二维码**
   - 李四将手机转向宾客："请扫这个码付款"
   - 宾客扫码付款 → 李四听到到账提示音
   - 李四输入宾客姓名「李秀英」、电话「139****5678」、金额「800」
   - 在备注中填写"付款微信：秀英姐"
   - 点击「提交」→ 所有客户端实时更新
   - 下一笔宾客也需要微信付款，但希望付给赵六
   - 李四**切换微信收款账户**为「赵六-微信2」
   - 界面下方**二维码自动更换**为赵六-微信2的收款码
   - 宾客扫码付款 → 记账提交

8. **微信限额预警场景**
   - 李四的微信-微信1已接近限额，剩余额度仅¥1,500
   - 下一笔宾客选择微信收款时，李四-微信1账户在选择列表中**标红显示**："剩余¥1,500"
   - 继续收款后，剩余¥180 **≤ 200**，该账户**置灰禁用**
   - 提示"该账户剩余额度不足，请切换其他账户"
   - 李四切换至赵六-微信2继续收款

9. **重名提醒场景**
   - 又有一位宾客自称「赵大伟」来随礼
   - 张三输入姓名「赵大伟」、金额「600」、备注"微信付款"
   - 点击提交时，系统检测到礼簿中已存在「赵大伟」记录
   - **弹出重名提醒**："礼簿中已有「赵大伟」的记录（¥500，代理4人，12:40:15）"
   - 弹窗中「备注已有记录」预填原记录备注（如空），「备注当前记录」预填"微信付款"
   - 张三确认这是另一位同名宾客 → 在「备注已有记录」中输入"同事，IT部门"以区分 → 点击「新增记录」→ 已有记录备注更新为"同事，IT部门"，新记录保存成功
   - 若张三确认是同一人追加随礼 → 点击「取消录入并编辑原记录」→ 关闭弹窗进入编辑页面，在原记录上补充信息

10. **宴席中途对账**
    - 宴席进行到一半，张三（现金收银员）和李四（微信收银员）决定先核对一下
    - 张三打开「对账」Tab → 筛选「现金-张三」
    - 张三清点手中现金¥15,200，与账面记录32笔金额一致
    - 批量勾选 → 标记为「已对账」
    - 李四同理核对微信转账记录（通过微信钱包与备注中的"付款微信"核对），与账面一致后标记「已对账」
    - 顶部进度更新："已对账 64笔 / 总96笔"

11. **漏记补记**
    - 宴席结束后发现漏记了早到的一位宾客「孙大爷」
    - 张三进入补记模式
    - 输入姓名「孙大爷」、金额「300」、收款方式「现金」
    - **手动设置记账时间**：12:05:33（实际到场时间）
    - 提交补记 → 记录按设定时间插入到正确位置

12. **宴席结束最终对账**
    - 进入「对账」Tab
    - 张三现金：32笔全部【已对账】
    - 王五现金：18笔全部【已对账】
    - 李四-微信1：28笔全部【已对账】
    - 赵六-微信2：18笔全部【已对账】
    - 所有记录均「已对账」，对账完成

13. **进入收尾与合并向导**
    - 张三确认宴席结束，点击「结束宴席」→ 礼簿进入「收尾中」状态
    - 多端协作会话关闭，系统自动弹出合并向导
    - 「王大壮」电话138****1234 + 姓名匹配 → **自动关联**，不进入推荐列表
    - 「赵大伟」（第一个）无电话，系统推荐「赵大伟（朋友）」→ **需手动确认**
    - 确认映射 → 执行合并（人员关联建立，记录仍留在礼簿中）

### 核心表结构说明

> **数据隔离原则**：所有业务表均包含 `owner_id` 外键关联 `users.id`，API 层通过 JWT 中的 `user_id` 自动过滤，确保每个用户只能访问自己的数据。

#### users 表（用户）

| 字段 | 类型 | 说明 |
| ------ | ------ | ------ |
| id | INTEGER PK | 自增主键 |
| username | VARCHAR(50) UNIQUE | 用户名，全局唯一 |
| password_hash | VARCHAR(200) | Argon2 哈希密码 |
| role | VARCHAR(20) | 角色：super_admin（系统级管理员，仅管理系统运维和配置，不参与任何账簿管理）/ admin（数据管理员，管理家庭组和审批）/ editor（普通用户，默认角色，完全控制自己的数据）/ viewer（只读用户，仅查看不修改）/ auditor（审计员，仅查看操作日志） |
| is_active | BOOLEAN | 是否启用，默认 true |
| created_at | DATETIME | 创建时间 |

#### guestbook 表（礼簿）

| 字段 | 类型 | 说明 |
| ------ | ------ | ------ |
| id | INTEGER PK | 自增主键 |
| owner_id | INTEGER FK | 创建者（关联 users.id），数据隔离 |
| name | VARCHAR(100) | 礼簿名称 |
| event_type | VARCHAR(30) | 事由类型，见「事件类型枚举定义」章节（婚礼/寿宴/满月酒/乔迁/升学/丧葬/其他） |
| event_date | DATE | 宴席日期 |
| status | VARCHAR(20) | 状态：active（收礼中）/ closing（收尾中）/ archived（已归档），应用层 Literal 校验 |
| created_at | DATETIME | 创建时间 |
| closing_at | DATETIME | 进入收尾阶段时间 |
| archived_at | DATETIME | 归档时间 |
| person_merged_at | DATETIME | 合并到人员库时间（nullable）；非空表示该礼簿已执行过合并，此后修改宾客姓名/电话的记录及补录记录自动重新解析 person_id |
| operator_note | TEXT | 创建者备注 |
| host_person_id | INTEGER FK | 关联主人家人员（可关联多个，主关联人存此字段；更多关联见 guestbook_host 表） |
| is_deleted | BOOLEAN | 软删除标记（默认 false），删除时设为 true，30 天后物理清除 |
| deleted_at | DATETIME | 删除时间（nullable），用于定时清理任务 |

#### guestbook_host 表（礼簿主人家关联）

| 字段 | 类型 | 说明 |
| ------ | ------ | ------ |
| id | INTEGER PK | 自增主键 |
| guestbook_id | INTEGER FK | 所属礼簿，ON DELETE CASCADE |
| person_id | INTEGER FK | 关联主人家人员，ON DELETE CASCADE |
| is_primary | BOOLEAN | 是否主要关联人（默认 false），与 guestbook.host_person_id 保持一致 |
| created_at | DATETIME | 关联创建时间 |

> **唯一约束**：guestbook_host 表对 (guestbook_id, person_id) 设置 UNIQUE 约束，同一礼簿不重复关联同一人员。
>
> **设计说明**：guestbook.host_person_id 存储主要关联人（冗余字段，便于快速查询），guestbook_host 表存储所有关联的主人家人员（包括主关联人）。一场宴席可能有多个主人家（如新郎家、新娘家），通过此表实现多对多关联。

| 字段 | 类型 | 说明 |

| 审批拒绝 | pending_approval | REJECT | 新增 |
| 安全模式切换 | user_key_config | SECURITY_SWITCH | 新增，记录 normal↔enhanced 切换 |
| 隐私标记变更 | daily_record / gb_record / person | PRIVACY_MARK | 新增，记录 is_private 字段变化 |

**设计说明：**

- 原 operation_log 仅覆盖 gb_record 操作，扩展后覆盖所有关键业务操作
- `target_table` + `target_id` 替代原 `gb_record_id`，实现通用化审计
- `guestbook_id` 保留为可选字段，便于按礼簿查询相关日志
- 安全模式切换、隐私标记等敏感操作必须记录，满足 NF-5 审计要求

### 外键级联规则

所有外键关系必须明确定义 `ON DELETE` 行为，确保数据一致性：

| 子表 | 外键字段 | 父表 | ON DELETE 行为 | 说明 |
| ------ | ---------- | ------ | ---------------- | ------ |
| gb_record | guestbook_id | guestbook | **CASCADE** | 删除礼簿时级联删除所有收礼记录 |
| gb_record | person_id | person | **SET NULL** | 删除人员时保留记录但解除关联 |
| gb_record | account_id | payment_account | **SET NULL** | 删除账户时保留记录但解除关联 |
| operation_log | guestbook_id | guestbook | **CASCADE** | 删除礼簿时级联删除操作日志 |
| operation_log | owner_id | users | **CASCADE** | 删除用户时级联删除操作日志 |
| terminal_settings | guestbook_id | guestbook | **CASCADE** | 删除礼簿时级联删除终端设置 |
| terminal_settings | default_cash_account | payment_account | **SET NULL** | 删除账户时清空默认设置 |
| terminal_settings | default_wechat_account | payment_account | **SET NULL** | 删除账户时清空默认设置 |
| daily_record | person_id | person | **SET NULL** | 删除人员时保留记录但解除关联 |
| daily_record | account_id | payment_account | **SET NULL** | 删除账户时保留记录但解除关联 |
| person_balance_adjustment | person_id | person | **CASCADE** | 删除人员时级联删除差额调整 |
| family_member | group_id | family_group | **CASCADE** | 删除家庭组时级联删除成员 |
| family_member | user_id | users | **RESTRICT** | 禁止删除有家庭成员的用户 |
| pending_approval | group_id | family_group | **CASCADE** | 删除家庭组时级联删除待审批 |
| pending_approval | submitter_id | users | **RESTRICT** | 禁止删除有待审批提交的用户 |
| pending_approval | reviewer_id | users | **SET NULL** | 删除审批人时保留记录 |
| user_key_config | user_id | users | **CASCADE** | 删除用户时级联删除加密配置 |
| guestbook_host | guestbook_id | guestbook | **CASCADE** | 删除礼簿时级联删除主人家关联 |
| guestbook_host | person_id | person | **CASCADE** | 删除人员时级联删除主人家关联 |

> **设计原则**：核心业务数据（礼簿、记录、日志）采用 CASCADE 确保数据完整性；人员与账户删除采用 SET NULL 保留历史记录；用户删除采用 RESTRICT 防止误删关联数据。

### 数据库索引定义

为满足 NF-1 性能要求（单礼簿 3000+ 记录），需建立以下复合索引：

| 表 | 索引字段 | 索引类型 | 用途 |
| ---- | ---------- | ---------- | ------ |
| guestbook | (owner_id, status, created_at DESC) | B-tree | 按用户和状态筛选礼簿列表 |
| gb_record | (guestbook_id, payment_method) | B-tree | 按礼簿和支付方式筛选记录 |
| gb_record | (guestbook_id, check_status) | B-tree | 按礼簿筛选对账状态 |
| gb_record | (guestbook_id, record_time) | B-tree | 按礼簿和时间排序 |
| gb_record | (guestbook_id, person_id) | B-tree | 按礼簿和人员查询 |
| gb_record | (uuid) | UNIQUE | 防重复写入（已定义） |
| daily_record | (owner_id, event_date DESC) | B-tree | 按用户和日期倒序查询 |
| daily_record | (owner_id, person_id) | B-tree | 按用户和人员查询 |
| daily_record | (owner_id, type, event_date) | B-tree | 按用户、类型、日期筛选 |
| person | (owner_id, name) | B-tree | 按用户和姓名搜索 |
| person | (owner_id, phone) | B-tree | 按用户和电话精确匹配 |
| operation_log | (owner_id, target_table, created_at DESC) | B-tree | 按用户、目标表、时间查询日志 |
| operation_log | (guestbook_id, created_at DESC) | B-tree | 按礼簿查询操作日志（兼容旧结构） |
| payment_account | (owner_id, type) | B-tree | 按用户和账户类型筛选 |
| family_member | (group_id, user_id) | UNIQUE | 家庭成员唯一约束（已定义） |
| pending_approval | (group_id, status, submitted_at) | B-tree | 按家庭组、状态、时间筛选审批 |
| terminal_settings | (guestbook_id, client_id) | UNIQUE | 终端设置唯一约束（已定义） |
| guestbook_host | (guestbook_id, person_id) | UNIQUE | 礼簿主人家关联唯一约束（已定义） |
| guestbook_host | (person_id) | B-tree | 按人员查询关联礼簿 |
| notification | (recipient_id, is_read, created_at DESC) | B-tree | 按接收人查询未读通知 |

> **索引策略**：独立业务表（daily_record、person、payment_account、operation_log）的索引以 `(owner_id, ...)` 开头确保数据隔离查询高效；关联表（gb_record、terminal_settings、guestbook_host）以 `(guestbook_id, ...)` 开头优化礼簿内查询；时间字段降序索引优化"最新记录"查询；UNIQUE 约束自动创建唯一索引。

### 事件类型枚举定义

系统统一定义以下 `event_type` 枚举值，日常模式和礼簿模式共用同一枚举集：

| 枚举值 | 中文名称 | 适用场景 | 说明 |
| -------- | ---------- | ---------- | ------ |
| wedding | 婚礼 | 日常 + 礼簿 | 结婚喜宴 |
| birthday | 生日/寿宴 | 日常 + 礼簿 | 日常称"生日"，礼簿称"寿宴"，前端按上下文显示不同文案 |
| fullmoon | 满月酒 | 日常 + 礼簿 | 婴儿满月宴 |
| housewarming | 乔迁 | 日常 + 礼簿 | 乔迁新居 |
| graduation | 升学 | 日常 + 礼簿 | 考上大学/研究生等 |
| funeral | 丧葬 | 日常 + 礼簿 | 丧事 |
| holiday | 节日红包 | 日常专用 | 春节、中秋等节日红包往来 |
| other | 其他 | 日常 + 礼簿 | 未分类事由 |

> **映射说明**：日常模式的"生日"和礼簿模式的"寿宴"在数据库中统一存储为 `birthday`，前端根据记录类型（daily_record vs gb_record）显示对应文案。日常模式独有 `holiday`（节日红包）类型，礼簿模式不显示此选项（宴席场景不适用）。

### 列表 API 分页规格

所有返回列表的 API 端点必须遵循统一分页规范：

**分页参数：**

- `page`：页码，从 1 开始，默认 1
- `page_size`：每页条数，默认 20，最大 100
- `sort_by`：排序字段（可选），如 `created_at`、`event_date`、`amount`
- `sort_order`：排序方向（可选），`asc` 或 `desc`，默认 `desc`

**响应信封格式：**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "items": [...],
    "pagination": {
      "page": 1,
      "page_size": 20,
      "total_count": 156,
      "total_pages": 8
    }
  }
}
```

**需分页的端点：**

- 日常记录列表（F-1.4）
- 礼簿列表（F-2.6）
- 礼簿收礼记录列表（F-2.7）
- 人员列表（F-9.1 人员档案）
- 操作日志列表（F-5.3 日志查看）
- 人员详情-按宴请查看（F-9.7）
- 待审批队列列表（F-11.13）
- 通知列表（F-11.20）

**特殊说明：**

- 单礼簿收礼记录超过 3000 条时，前端采用虚拟滚动（virtual scrolling），后端仍按分页返回
- 人员搜索、礼簿筛选等带查询条件的接口同样遵循分页规范
- 首页概览（Dashboard）的"最近记录"固定返回 5 条，不分页

### 7.4 部署架构

```text
┌──────────────┐      ┌──────────────────┐      ┌──────────────┐
│   客户端A     │◄────►│  FastAPI 后端     │◄────►│   客户端B    │
│  (手机/平板/电脑)│ wss │  (Uvicorn+async) │ wss │ (手机/平板/电脑)│
└──────┬───────┘      └────────┬─────────┘      └──────┬───────┘
       │                       │                        │
       │  本地IndexedDB         │  PostgreSQL 17         │  本地IndexedDB
       │  (主存储)              │                        │  (主存储)
       │                       │                        │
       │  ┌─────────────────┐  │  ┌─────────────────┐   │  ┌─────────────────┐
       │  │ 客户端加密层     │  │  │ 服务端加密层     │   │  │ 客户端加密层     │
       │  │ (增强模式可选)   │  │  │ (普通模式默认)   │   │  │ (增强模式可选)   │
       │  │ AES-256-GCM     │  │  │ 服务端管理密钥   │   │  │ AES-256-GCM     │
       │  │ 密钥不离设备     │  │  │                  │   │  │ 密钥不离设备     │
       │  └─────────────────┘  │  └─────────────────┘   │  └─────────────────┘
       ▼                       ▼                        ▼
┌──────────────┐      ┌──────────────────┐      ┌──────────────┐
│  日常记录存档 │      │  礼簿同步会话     │      │  日常记录存档 │
│  礼簿长期保留 │      │  用户/权限/审计   │      │  礼簿长期保留 │
│  隐私数据隔离 │      │  家庭组/成员      │      │  隐私数据隔离 │
└──────────────┘      │  家庭共享数据池   │      └──────────────┘
                      │  待审批队列       │
                      │  加密配置(密文)   │
                      └──────────────────┘
```

> 注：采用**本地优先（Local-first）**架构。IndexedDB 为主存储，日常记录默认仅存本地。加入家庭组后，数据按需同步至 PostgreSQL 服务端，供家庭成员共享。「隐私记录」标记的数据同步至云端但仅本人可查看，通过权限隔离实现隐私保护。礼簿现场协作期间数据通过 WebSocket 实时同步，协作结束后礼簿数据长期保留在客户端本地。PostgreSQL 存储用户账户、权限、家庭组、审批队列等需要持久化和服务端共享的数据。**增强安全模式**下，客户端在同步前使用 AES-256-GCM 加密数据，服务端仅存储密文，实现零知识架构。

## 九、风险与约束

| 风险 | 影响 | 缓解措施 |
| ------ | ------ | ---------- |
| 用户担心隐私不愿使用 | 高 | 本地优先架构：日常数据默认不上云；「隐私记录」标记确保敏感数据仅本人可见；家庭共享按需开启；明确隐私政策 |
| 多客户端同步冲突 | 高 | UUID防重复写入；冲突记录人工确认机制；操作日志完整可追溯 |
| 现场网络不稳定 | 高 | 离线暂存 + 断网续传；本地优先写入，异步后台同步 |
| 微信限额导致收款中断 | 高 | 限额预警（<¥2000标红，≤¥200禁用）+ 多账户切换 + 备用账户快速启用 |
| 对账遗漏或错误 | 高 | 对账状态可视化 + 中途对账提醒 + 可随时取消对账重新核对 |
| 代理送礼记录混乱 | 中 | 被代理人记录等级平级 + 可分别设置支付方式 + 经办人字段追溯 |
| 老年用户操作困难 | 中 | 大字号模式、简化流程、语音输入（可选）、操作引导 |
| 数据丢失 | 高 | 定期自动备份提示、一键导出、礼簿归档前提醒导出 |
| 同名宾客误识别 | 中 | 电话+姓名（含同音字）精确匹配优先；智能推荐仅作参考，最终由用户确认 |
| 恶意客户端篡改数据 | 中 | 操作日志防篡改；关键操作二次确认；礼簿创建者拥有最高权限 |
| 家庭共享数据冲突 | 中 | 增量同步+版本号机制；家人修改需主账户审批；「隐私记录」标记保护敏感数据 |
| 云端同步数据泄露 | 高 | 传输层 TLS 加密；「隐私记录」服务端权限隔离；家庭组邀请码时效限制；敏感数据按需同步；增强安全模式下客户端零知识加密，服务端无法解密 |
| 增强模式密钥丢失 | 高 | 生成密钥时强制引导用户抄录恢复助记词（12/24词）；助记词离线保存，不上传服务端；提供密钥导出备份功能；明确告知用户"丢失助记词=丢失数据"的风险 |
