# 协作邀请功能方案审查意见

## 总体结论

方案本身流程闭环、安全考虑（防枚举、数据隔离、懒过期检测）写得比较完整，**但按现状直接实施会产生两套并行的授权体系，且"接受邀请后协作人员如何真正访问礼簿"这一核心链路在设计中是缺失的**。建议修订后再动手。

## 现状核实（与代码对照）

方案列出的全部文件目前均不存在，属于全新功能：后端无 `collaboration_invite.py` 模型、无 `collaboration.py` API、无对应 Schema；前端无 `CollaborationPage.tsx`，`types/index.ts`、`api-client.ts`、`useQueries.ts` 中也无相关代码。[协作邀请功能方案](kimi-cite://md-line?path=D%3A/web/GiftRegistry/docs/%E5%8D%8F%E4%BD%9C%E9%82%80%E8%AF%B7%E5%8A%9F%E8%83%BD%E6%96%B9%E6%A1%88.md&line=112&text=server%2Fapp%2Fapi%2Fcollaboration.py "citation")

但项目里**已有一套功能等价的「协助邀请」实现**，方案只字未提：

- 后端 `authorization.py`：礼簿所有者生成 16 位授权码，指定被授权人账号、权限（record/reconcile/both）和过期时间，被授权人在授权码页面输入绑定，可撤销、有日志。[authorization](kimi-cite://text?path=D%3A/web%2FGiftRegistry%2Fserver%2Fapp%2Fapi%2Fauthorization.py&text=secrets.token_urlsafe%2816%29%5B%3A16%5D.upper%28%29 "citation")
- 前端 `GuestbookPage.tsx` 已内嵌「协助邀请」弹窗：用户名模糊搜索选人 → 生成授权码 → 展示当前邀请列表并可撤销。[GuestbookPage](kimi-cite://text?path=D%3A/web%2FGiftRegistry%2Fweb%2Fsrc%2Fpages%2FGuestbookPage.tsx&text=function%20InviteModal%28%7B%20guestbookId%2C%20onClose%20%7D "citation")

## 主要问题

### P0-1：与现有 authorization_codes 体系的关系未交代

新旧两套机制业务目标完全相同（非家庭成员 + 指定礼簿 + 限时 + 分权限）。方案没有"现状与差异"章节，没说清是**替代**还是**共存**：
