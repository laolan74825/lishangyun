**用户：** SMTP 授权码写在代码里安全吗？

不安全，**不建议把 SMTP 授权码写死在代码里**，也不建议直接明文提交到 `.env` 再提交进 git。不过好消息是：**这个项目当前的方案正好就是规避这个风险的**，你不需要往代码里写任何东西。

这个项目的做法是（前面看过的代码）：

1. 授权码**不落代码、不落明文配置文件**，而是由管理员在后台「系统设置」页面填写，后端用 AES-256 加密后存进数据库的 `system_settings.smtp_password_enc` 字段（[admin.py](D:\web\GiftRegistry\server\app\api\admin.py)）。
2. 使用时后端解密取出，通过 smtplib 连接 SMTP 服务器发送，用完即弃，不写入日志。
3. 加密用的密钥是 `APP_ENCRYPTION_KEY`（在 `.env` 中，且不提交 git——`.env.example` 里只有全零占位值）。

这套设计能挡住的风险：

- 代码仓库、前端打包产物里完全没有授权码；
- 数据库泄露时，攻击者拿到的只是密文，没有 `APP_ENCRYPTION_KEY` 解不开；
- 后台接口回读设置时只返回 `smtp_password_set: true/false`，不会把密码回显给前端。

仍要注意的几点（这是方案的安全边界，不是缺陷）：

- `APP_ENCRYPTION_KEY` 本身要保护好：生产环境用随机生成的 64 位十六进制串（`openssl rand -hex 32`），不要沿用默认值——代码里已有 fail-fast 校验，生产环境用默认密钥会直接拒绝启动。
- 密钥和数据库要分开保管，别备份到同一个不受控的位置，否则加密形同虚设。
- 授权码一旦怀疑泄露（比如管理员账号被盗），去邮箱服务商后台**作废重发一个**，再到后台设置页更新即可，不用改代码。

所以结论是：写代码里 ❌；走这个项目的「后台配置 + 数据库存密文」方案 ✅。日常运维你只需要管好管理员账号和 `APP_ENCRYPTION_KEY`。

1. **后端路由尾部斜线问题**：`operation_logs.py` 等 8 个路由文件把接口定义在带斜线的路径上（如 `/operation-logs/`），而前端请求不带斜线，Starlette 于是返回 307 重定向到**绝对地址** `http://localhost:8000/...`。
2. **浏览器跨源重定向剥掉 Authorization**：前端经 vite 代理（5173 端口）请求，跟随重定向等于跨到 8000 端口这个"不同源"，浏览器按规范剥掉 Authorization 头 → 后端返回 401。
3. **前端的 401 处理是"登出式"的**：`api.ts` 一遇 401 就清 token 并 `location.href = '/login'`（整页刷新），所以你看到"新页面闪现一下又跳回登录页"。后台仪表盘恰好挂载时就请求审计日志接口，于是必触发。
4. **为什么 curl 测不出来**：curl 跟随重定向时会保留 Authorization 头，所以同样的请求用 curl 一直是 200，只有浏览器会翻车。

**做的三处修复**

- [main.py](D:\web\GiftRegistry\server\app\main.py)：加了相对重定向中间件，把后端 307 的绝对 Location 改成相对路径，浏览器会沿用当前源（走代理），Authorization 不再丢失——一处修复覆盖全部 15 个同类路由。
- [vite.config.ts](D:\web\GiftRegistry\web\vite.config.ts)：代理目标从 `localhost` 改为 `127.0.0.1`。这里还有个小插曲：你机器上 Docker Desktop 的端口转发还占着 8000/5432（`com.docker.backend`），`localhost` 优先解析到 IPv6 会连上一个**跑旧代码的容器**，改 IPv4 后走到的才是本地源码运行的后端。
- 重启了本地后端（你原来的 uvicorn 进程 watch 失效且已被我结束，我用相同参数在后台重新拉起了）。

**验证结果**：浏览器真实走完 登录 → /admin → 审计日志接口 全链路 200，页面稳定在管理后台；后端 22 个认证测试全部通过。
