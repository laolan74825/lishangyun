# 协作邀请功能方案

> 邀请码机制：授权人通过邮箱精确查找对方用户，发送协作邀请并生成 6 位邀请码，对方在首页收到邀请信号后输入邀请码完成接受。

---

## 1. 功能概述

协作邀请功能允许礼簿所有者（授权人）邀请非家庭成员的协作人员在指定时间段内协助管理特定礼簿。核心流程：

1. 授权人在礼簿页面点击「协助邀请」，输入对方**注册邮箱**精确查找用户
2. 设置权限和有效期，点击发送 → 系统生成 **6 位邀请码**，同时向对方发送**邀请信号**
3. 邀请信号 **10 分钟内有效**，对方登录后在**首页**看到「接受协助邀请」按钮
4. 点击按钮后显示邀请码输入框，输入 6 位邀请码确认身份，接受邀请；或点击「拒绝」直接拒绝邀请
5. 授权人可随时撤销授权

### 1.1 设计要点

- **邮箱精确查找**：避免姓名重复导致的误邀，通过注册邮箱唯一确定对方
- **6 位邀请码**：防止邮箱输错时误绑，对方收到邀请信号后需核对邀请码确认
- **10 分钟信号有效期**：邀请信号仅在 10 分钟内展示在首页，超时需重新发送
- **实时通知**：已登录的对方立即看到邀请；10 分钟内登录的对方也能看到

### 1.2 与家庭成员的区别

| 维度 | 家庭成员 | 协作人员 |
|------|---------|---------|
| 关系 | 长期家庭关系 | 临时协作关系 |
| 范围 | 可访问所有礼簿 | 仅访问指定礼簿 |
| 时间 | 无期限 | 有明确截止时间 |
| 加入方式 | 家庭组邀请码 | 邮箱邀请 + 邀请码确认 |

## 2. 数据模型

### 2.1 CollaborationInvite（协作邀请）

**文件**：`server/app/models/collaboration_invite.py`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer, PK | 自增主键 |
| inviter_id | Integer, FK→users.id | 邀请人（礼簿所有者），CASCADE 删除 |
| invitee_id | Integer, FK→users.id | 被邀请人（协作人员），CASCADE 删除 |
| guestbook_id | Integer, FK→guestbooks.id | 关联礼簿 |
| invite_code | String(6), indexed | 6 位数字邀请码 |
| permissions | String(10), default "record" | 权限类型：record / reconcile / both |
| status | String(10), default "pending" | 状态：pending / accepted / rejected / revoked / expired |
| signal_expires_at | DateTime | 邀请信号过期时间（创建时间 + 10 分钟） |
| collaboration_days | Integer | 协作天数（接受后从接受时刻开始计算） |
| accepted_at | DateTime, nullable | 接受时间 |
| collaboration_expires_at | DateTime, nullable | 协作截止时间（接受时计算：accepted_at + collaboration_days） |
| created_at | DateTime | 创建时间 |

**约束**：
- 同一邀请人对同一被邀请人、同一礼簿，不允许存在多个 pending 状态的邀请（防重复发送）

**索引**：
- `invitee_id + status` 复合索引（首页查询待处理邀请）
- `invite_code` 索引（接受邀请时查找）
- `inviter_id + guestbook_id` 复合索引（查询某礼簿的邀请列表）

**数据隔离**：邀请人查询过滤 `inviter_id == current_user.id`；被邀请人查询过滤 `invitee_id == current_user.id`。

### 2.2 AuthorizationActionLog（操作日志）

**文件**：`server/app/models/authorization_action_log.py`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer, PK | 自增主键 |
| invite_id | Integer, FK→collaboration_invites.id | 关联邀请 |
| action_type | String(20) | SEND / ACCEPT / REJECT / REVOKE |
| operator_id | Integer, FK→users.id | 操作人 |
| detail | Text, nullable | 操作详情描述 |
| created_at | DateTime | 操作时间 |

### 2.3 状态流转

```
         发送
          ↓
      ┌──────────┐
      │ pending  │ ←── 初始状态（信号 10 分钟有效）
      └────┬─────┘
           │
     ┌─────┼──────────┬──────────┐
     ↓     ↓          ↓          ↓
┌──────────┐ ┌─────────┐ ┌────────┐ ┌─────────┐
│ accepted │ │ rejected│ │revoked │ │expired  │
└────┬─────┘ └─────────┘ └────────┘ └─────────┘
     │
     ↓
┌────────┐
│revoked │  （accepted 状态也可撤销）
└────────┘
```

- **pending**：已发送，等待对方接受或拒绝（信号 10 分钟内可见）→ 可取消邀请
- **accepted**：对方已接受邀请，协作关系生效 → 可撤销授权
- **rejected**：对方已拒绝邀请（终态）
- **revoked**：已被授权人撤销（pending 取消邀请 或 accepted 撤销授权）
- **expired**：信号超时（10 分钟内未操作），查询时自动从 pending 转为 expired（终态）

**注意**：信号过期（pending → expired）与协作过期是两个独立概念。信号过期后需重新发送邀请；协作过期是指 `collaboration_expires_at` 到达后协作权限失效。

## 3. 后端 API

**文件**：`server/app/api/collaboration.py`
**路由前缀**：`/api/collaboration`

### 3.1 通过邮箱查找用户

```
GET /api/collaboration/search?email=user@example.com
```

**查询参数**：
- `email`（必填）：精确匹配用户注册邮箱

**响应**：

```json
{
  "id": 5,
  "username": "zhangsan",
  "email": "user@example.com"
}
```

**业务逻辑**：
1. 精确匹配邮箱查找用户（大小写不敏感）
2. 不能查找自己（`id != current_user.id`）
3. 找不到时返回 404，不暴露用户是否存在（统一返回"未找到该邮箱对应的用户"）

### 3.2 发送协作邀请

```
POST /api/collaboration/invites
```

**请求体**（CollaborationInviteCreate）：

```json
{
  "invitee_email": "user@example.com",
  "guestbook_id": 1,
  "permissions": "record",
  "collaboration_days": 7
}
```

**响应**：

```json
{
  "id": 1,
  "invite_code": "385721",
  "invitee_email": "user@example.com",
  "signal_expires_at": "2026-09-30T10:10:00",
  "collaboration_days": 7
}
```

**业务逻辑**：
1. 通过邮箱精确查找被邀请人（同 3.1 逻辑）
2. 验证礼簿存在且属于当前用户
3. 验证 `collaboration_days > 0`
4. 检查重复邀请：查询是否已存在 `inviter_id + invitee_id + guestbook_id + status=pending` 的记录，存在则拒绝
5. 生成 6 位数字邀请码：`secrets.randbelow(1000000)` 补零至 6 位
6. 计算信号过期时间：`datetime.utcnow() + timedelta(minutes=10)`
7. 写入 `CollaborationInvite`（status=pending，`collaboration_expires_at=null`）
8. 写入 `AuthorizationActionLog`（action_type=SEND）
9. 返回邀请码（仅此时展示一次，供授权人告知对方核对）

### 3.3 查询我的待处理邀请（首页用）

```
GET /api/collaboration/invites/pending
```

**响应**：`CollaborationInvitePendingResponse[]`

```json
[
  {
    "id": 1,
    "inviter_id": 2,
    "inviter_username": "李四",
    "guestbook_id": 1,
    "guestbook_name": "婚礼礼金",
    "permissions": "record",
    "signal_expires_at": "2026-09-30T10:10:00",
    "created_at": "2026-09-30T10:00:00"
  }
]
```

**业务逻辑**：
1. 查询 `invitee_id == current_user.id` 且 `status == "pending"`
2. 查询时自动将 `signal_expires_at < now()` 的记录标记为 expired
3. 关联查询邀请人用户名和礼簿名称
4. 按 `created_at DESC` 排序

### 3.4 接受邀请

```
POST /api/collaboration/invites/accept
```

**请求体**（CollaborationInviteAcceptRequest）：

```json
{
  "invite_id": 1,
  "invite_code": "385721"
}
```

**响应**：

```json
{
  "message": "已接受协作邀请",
  "guestbook_id": 1,
  "permissions": "record",
  "collaboration_expires_at": "2026-10-07T09:00:00"
}
```

**业务逻辑**：
1. 按 `invite_id` 查找邀请，验证 `invitee_id == current_user.id`
2. 验证状态为 pending
3. 验证信号未过期（`signal_expires_at > now()`），否则标记 expired 并拒绝
4. 验证邀请码匹配（`invite_code == 请求的 invite_code`）
5. 更新状态为 accepted，记录 `accepted_at = now()`
6. 计算协作截止时间：`collaboration_expires_at = accepted_at + timedelta(days=collaboration_days)`
7. 写入 `AuthorizationActionLog`（action_type=ACCEPT）

### 3.5 拒绝邀请

```
POST /api/collaboration/invites/{invite_id}/reject
```

**响应**：`{ "message": "邀请已拒绝" }`

**业务逻辑**：
1. 按 `invite_id` 查找邀请，验证 `invitee_id == current_user.id`
2. 验证状态为 pending（信号过期后会自动标记为 expired，此处无需额外检查）
3. 更新状态为 rejected
4. 写入 `AuthorizationActionLog`（action_type=REJECT）

### 3.6 查询我发出的邀请列表

```
GET /api/collaboration/invites?guestbook_id=1&status=active
```

**查询参数**：
- `guestbook_id`（可选）：按礼簿筛选
- `status`（可选）：按状态筛选（active 表示 pending + accepted）

**响应**：`CollaborationInviteResponse[]`

**业务逻辑**：查询 `inviter_id == current_user.id`，查询时自动将过期的 pending 标记为 expired。

### 3.7 查询我接受的协作列表

```
GET /api/collaboration/invites/accepted
```

**响应**：`CollaborationInviteAcceptedResponse[]`

```json
[
  {
    "id": 1,
    "inviter_id": 2,
    "inviter_username": "李四",
    "guestbook_id": 1,
    "guestbook_name": "婚礼礼金",
    "permissions": "record",
    "collaboration_expires_at": "2026-10-07T10:05:00",
    "accepted_at": "2026-09-30T10:05:00"
  }
]
```

**业务逻辑**：
1. 查询 `invitee_id == current_user.id` 且 `status == "accepted"`
2. 查询时自动将 `collaboration_expires_at < now()` 的记录标记为 expired（协作过期）
3. 关联查询邀请人用户名和礼簿名称
4. 按 `accepted_at DESC` 排序

### 3.8 撤销邀请（取消邀请 / 撤销授权）

```
POST /api/collaboration/invites/{invite_id}/revoke
```

**响应**：`{ "message": "邀请已撤销" }` 或 `{ "message": "授权已撤销" }`

**业务逻辑**：
1. 验证邀请的 `inviter_id == current_user.id`
2. 验证状态为 pending 或 accepted（expired 和 revoked 不可操作）
3. 更新状态为 revoked
4. 写入 `AuthorizationActionLog`（action_type=REVOKE）

**场景说明**：
- **pending 状态**：取消邀请（对方尚未接受）
- **accepted 状态**：撤销授权（协作期间终止协作关系）

前端根据状态显示不同按钮文案和确认提示。

### 3.9 查询操作日志

```
GET /api/collaboration/invites/{invite_id}/logs
```

**响应**：`AuthorizationActionLogResponse[]`

### 5.4 页面与组件

#### 入口一：礼簿页面的邀请弹窗（InviteModal）

**文件**：`web/src/pages/GuestbookPage.tsx`（内嵌组件）

**触发方式**：礼簿卡片上的「协助邀请」按钮。

**交互流程**：
1. 输入对方**注册邮箱**（精确匹配），点击查找或失焦触发
2. 查找成功后显示对方用户名，确认邀请对象
3. 选择权限：仅记账 / 仅对账 / 记账+对账
4. 输入协作天数（数字输入框，1~365天）
5. 点击「发送邀请」→ 调用 `createCollaborationInvite`
6. 发送成功后显示：
   - **6 位邀请码**（大字展示，可一键复制）
   - 提示文案："请将邀请码告知对方，对方在首页接受邀请时需输入此码"
   - 信号有效期倒计时（10 分钟）
   - 提示文案："协作时长：对方接受后 X 天内有效"
7. 底部显示该礼簿当前有效的邀请列表（pending + accepted）

**关键状态**：
- `emailInput`：邮箱输入
- `foundUser`：查找到的用户信息
- `permissions`：权限选择
- `collaborationDays`：协作天数（数字）
- `generatedInviteCode`：发送成功后存储邀请码

#### 入口二：首页待处理邀请通知

**文件**：`web/src/pages/DashboardPage.tsx`（内嵌组件）

**触发方式**：用户登录后自动查询 `usePendingInvites()`。

**展示方式**：
- 有待处理邀请时，在首页顶部显示邀请卡片（可多条）
- 每张卡片显示：
  - 「**XXX 邀请你协助管理「YYY」礼簿**」
  - 权限说明 + 信号剩余时间倒计时
  - 「接受邀请」按钮 + 「拒绝」按钮
- 无待处理邀请时不显示任何内容

**接受邀请流程**：
1. 点击「接受邀请」按钮
2. 弹出邀请码输入框（6 位数字）
3. 输入邀请码，点击确认
4. 调用 `acceptCollaborationInvite`
5. 成功后显示成功提示，卡片消失

**拒绝邀请流程**：
1. 点击「拒绝」按钮
2. 弹出确认对话框："确定拒绝此协作邀请？"
3. 确认后调用 `rejectCollaborationInvite`
4. 成功后卡片消失

#### 入口三：协作人员管理页面（CollaborationPage）

**文件**：`web/src/pages/CollaborationPage.tsx`

  - pending 状态：「取消邀请」按钮 + 「日志」按钮

- 撤销授权确认文案："确定撤销此协作授权？撤销后对方将无法继续协助管理该礼簿。"

- 列表展示：邀请人 + 礼簿 + 权限 + 协作截止时间 + 状态（有效/已过期）
- 已过期的协作灰显，不可操作

## 7. 安全设计

### 7.1 邀请码生成

- 使用 `secrets.randbelow(1000000)` 生成 6 位数字，补零至 6 位
- 碰撞概率：100 万分之一，对于短期有效的邀请码足够安全
- 数据库可不加 UNIQUE 约束（10 分钟有效期 + 低并发场景）

### 7.2 邮箱查找

- 精确匹配，不支持模糊搜索，防止枚举用户
- 找不到时返回统一错误信息，不暴露用户是否存在
- 不能查找自己

### 7.3 数据隔离

- 邀请人查询：强制 `inviter_id == current_user.id`
- 被邀请人查询：强制 `invitee_id == current_user.id`
- 接受邀请：同时验证 `invitee_id` 和 `invite_code`

### 7.4 有效期检测

**信号过期**（10 分钟）：
- 邀请信号固定 10 分钟有效，不可配置
- 采用懒检测策略：查询时自动将过期的 pending 标记为 expired
- 超时后首页不再展示该邀请，授权人需重新发送

**协作过期**（天数）：
- 协作截止时间从接受时刻开始计算（`accepted_at + collaboration_days`）
- 采用懒检测策略：查询已接受协作列表时，自动将 `collaboration_expires_at < now()` 的记录标记为 expired
- 协作过期后，协作人员对该礼簿的操作权限失效
- 在协作人员执行操作时，后端需额外验证 `collaboration_expires_at > now()`

### 7.5 时区处理

后端使用 `datetime.utcnow()` 计算时间，所有时间字段存储为无时区的 UTC 时间。前端展示时根据用户时区转换显示。
