## 一、项目概述

### 1.1 产品定位

礼尚云是一款面向中国家庭的礼金往来记账工具，支持多账户独立注册与数据隔离，覆盖两大核心场景：

- **日常记账**：个人/家庭的人情往来送收记录，长期维护关系账本
- **现场收礼**：婚礼、寿宴等场合的多终端协作收礼，支持多收银员同时记账、实时对账

### 1.2 核心价值

- 替代传统纸质礼簿，实现电子化记账与对账
- 多账户独立注册，数据完全隔离，可灵活邀请协作
- 多终端（手机/平板/电脑）同时收礼，实时同步
- 自动统计与分析人情往来数据
- 本地优先架构（IndexedDB 主存储 + PostgreSQL 云端备份/家庭共享）
- 双安全模式（普通模式默认零摩擦、增强模式零知识加密）
- 离线可用，隐私优先（日常数据本地存储，隐私记录仅本人可见）

### 1.3 目标用户

主要用户为需要管理人情往来的家庭，典型使用场景包括婚礼、满月酒、寿宴、乔迁等宴请场合。用户技术水平参差不齐，需兼顾易用性与专业性。

### 4.3 关键约定

- **金额单位**：所有金额字段使用 `Integer`，单位为**分**（100 = ¥1.00），前端展示转换为"元"
- **owner_id 数据隔离**：所有业务表必须添加 `owner_id` 外键关联 `users.id`（⚠️ 当前尚未实现，P0 优先级）
- **软删除**：gb_record、daily_record、person、payment_account、guestbook 表均含 `is_deleted`（BOOLEAN，默认 false）+ `deleted_at`（DATETIME，nullable），删除时标记，30 天后物理清除
- **枚举样式字段**：使用 `String` + 应用层校验（`Literal` 类型），不使用数据库 ENUM
- **JSON 文本字段**：Person 别名通过 `@property` 以 JSON 字符串存取；操作日志 before_data/after_data 使用 JSONB
- **不可变日志**：`operation_logs` 表禁止 UPDATE/DELETE，采用通用 target_table + target_id 模式覆盖 16+ 操作类型
- **隐私与同步字段**：daily_record、person 表含 `is_private`（隐私记录标记）和 `sync_version`（增量同步版本号）
- **外键级联**：详见需求分析 §5.4 外键级联规则表（17 条 FK 关系定义 CASCADE/SET NULL/RESTRICT）
- **索引策略**：独立业务表（daily_record、person、payment_account、operation_log）以 `(owner_id, ...)` 开头；关联表（gb_record、terminal_settings、guestbook_host）以 `(guestbook_id, ...)` 开头；详见需求分析 §5.5 索引定义
- **金额验证**：最小 100 分（¥1）、单笔最大 1000 万分（¥100,000）、现金超 5 万需二次确认

## 六、角色与权限体系

### 6.1 当前状态（2026-10-01 已落地）

系统已实现 **3 级角色体系**，`users.role` 仅使用三个值：

| 角色 | 标识 | 来源 | 权限范围 |
| ------ | ------ | ------ | ---------- |
| 超级管理员 | `super_admin` | 系统首个注册用户自动产生 | 全部系统管理权限：授权/创建系统管理员、用户管理、系统配置、审计日志；账户受保护，不可被改角色、禁用或删除 |
| 系统管理员 | `admin` | 超级管理员授权（一般用户升级）或直接创建 | 管理后台日常管理：查看用户、创建一般用户、公告与系统配置等；**无权**授权他人为系统管理员 |
| 一般用户 | `user` | 注册用户一律为此角色 | 个人数据完全控制 |

### 6.2 历史规划变更说明

早期需求分析曾定义 5 级角色体系（super_admin / admin / editor / viewer / auditor）及子管理员权限点机制，**该方案已废止**（2026-10-01）：

- `editor` / `viewer` / `auditor` 从未进入数据库，前端类型中已移除；
- 历史遗留角色值 `family_member` / `collaborator` 经迁移 `g8h9i0j1k2l3_m7_normalize_user_roles` 统一归位为 `user`；
- 礼簿级协作权限不再依赖用户角色，由协作邀请（`collaboration_invites`，含 record/reconcile/both 权限）承载；
- 接口层 `RoleType = Literal["super_admin", "admin", "user"]`，管理接口的角色参数仅接受 `admin | user`（超级管理员不通过接口授予）。

### 6.3 安全原则

- 密码重置只能由用户本人通过安全邮箱验证码操作，管理员无权重置任何用户密码
- 所有业务查询必须按 `owner_id` 过滤，确保数据隔离
- 操作日志不可变（禁止 UPDATE/DELETE）

## 八、开发规范

### 8.1 后端规范

**代码风格：**

- 函数签名必须有完整类型注解
- 所有端点使用 `async def`，数据库操作通过 `AsyncSession`
- 新代码使用 `Annotated[Type, Depends(...)]` 依赖注入模式
- snake_case 命名函数/变量，PascalCase 命名类
- 导入分组：stdlib → third-party → app-local
- 使用 Ruff 统一代码风格（替代 flake8/black/isort）

**FastAPI 模式：**

- 每个模块一个路由文件，`APIRouter(prefix="/resource", tags=["resource"])`
- 404 消息按资源类型："礼簿不存在"/"记录不存在"/"人员不存在"/"账户不存在"/"用户不存在"
- 金额字段使用 `Field(..., ge=0)` 验证
- 枚举字符串使用 `Literal["val1", "val2"]`
- 密码哈希使用 Argon2（passlib），新注册直接使用；旧 bcrypt 哈希在下次登录时自动升级

**性能要求：**

- 所有列表端点必须实现分页（默认 limit=20，最大 100）
- 使用 `func.count()` / `func.sum()` 在数据库层聚合，禁止 Python 层循环
- 所有 `ForeignKey` 和 `owner_id` 列必须有 `index=True`
- 目标：单礼簿 3000+ 记录流畅运行
- JSON 字段使用 PostgreSQL JSONB 类型（如 `draft_data`、`detail`）

**审计日志：**

- 所有业务表（gb_record / daily_record / person / guestbook / payment_account 等）的增删改必须创建 `operation_log` 条目
- 使用通用模式：`target_table`（被操作表名）+ `target_id`（被操作记录 ID）+ `owner_id`（操作者）
- 关键字段：`action_type`（CREATE/UPDATE/DELETE/MERGE/ARCHIVE 等）、`before_data`、`after_data`（JSONB）
- `default=str` 处理 datetime 序列化

### 8.2 前端规范

**10 条硬约束：**

1. TypeScript strict 模式，禁止 `any`
2. 组件函数组件 + Hooks（React Compiler 自动优化，无需手动 memo/useCallback）
3. 服务端状态使用 TanStack Query 5（数据获取/缓存/失效重取/乐观更新）
4. 客户端状态使用 Zustand 5（终端设置/UI 状态/锁定状态）
5. API 调用统一通过 api-client，配合 TanStack Query 的 `queryFn`
6. 日期处理使用 dayjs
7. 样式使用 Tailwind CSS 4（`@theme` CSS-first 配置），不引入额外 CSS 文件
8. 路由使用 TanStack Router（编译时类型安全，`beforeLoad` 权限守卫）
9. PWA 支持（vite-plugin-pwa，Service Worker + 离线缓存策略）
10. 响应式布局使用 mobile-first + 容器查询（`@container`）

**代码模式：**

- 页面组件放 `pages/`，可复用组件放 `components/`
- 每个页面一个目录或一个文件（当前为单文件模式）
- 认证状态通过 TanStack Router 的 `beforeLoad` 检查，受保护路由使用 `loader` 预取数据
- TanStack Query 的 `queryKey` 使用工厂函数模式（如 `queryKeys.persons.list()`）

### 8.3 数据库迁移

```bash
cd server
alembic revision --autogenerate -m "description"
alembic upgrade head        # 应用
alembic downgrade -1        # 回退一步
alembic check               # 验证模型/迁移一致性
```

规则：

- 永远不修改已应用的迁移，创建新的
- 必须写可工作的 `downgrade()` 函数
- 审查自动生成的脚本（Alembic 可能误判）

### 8.4 错误处理与故障可见性（2026-10-01 新增）

**核心原则：任何请求失败都必须让用户知情，禁止静默失败。**详见《2026-10-01-全局错误提示与故障可见性改造汇总.md》。

后端：

- 全局异常处理器统一在 `app/core/errors.py` 注册（`main.py` 调用 `register_exception_handlers`），按异常类型分流：
  - 数据库连接层故障（`OperationalError` / `InterfaceError` / `connection_invalidated` 的 `DBAPIError` / 底层 `OSError`）→ **503** + 「数据库连接失败，请确认数据库服务已启动后重试」
  - 其他未处理异常 → **500** + 中性提示，堆栈只进日志不外泄
- 新增异常分类时同步补充 `tests/test_db_error_handler.py` 用例

前端：

- react-query 查询/变更的失败由 `queryClient.ts` 全局钩子统一提示，页面无需重复处理；个别查询确需静默时设 `meta: { silent: true }` 并注释理由
- 错误分级：网络不可达（`ApiError status=0`）与后端 503 → toast-bus 常驻横幅，任一请求成功后自动撤下；其他业务错误 → 红色 toast（4 秒节流去重、5 秒自动消失）
- `api-client.ts` 中「失败返回 undefined」语义的查询函数：仅 404 等业务错误可返回 undefined，**网络层错误必须抛出**交给全局提示
- 直接调用 `api.get/post/...` 的地方禁止空 `.catch(() => {})`；后台非关键操作（如 IndexedDB 缓存写入）除外
- 新增全局提示统一走 `toast-bus.ts` 的 `showGlobalToast`，由 `GlobalToast` 组件渲染；错误底色用 `bg-danger`（#c0392b）

### 9.3 隐私与安全

**本地优先架构：**

- IndexedDB 为主存储，PostgreSQL 为持久备份与家庭共享源
- 日常记录默认仅存本地，加入家庭组后按需同步至服务端
- 「隐私记录」标记（is_private）的数据同步至云端但仅本人可查看，家人不可见

**双安全模式：**

- **普通安全**（默认）：TLS 传输 + 服务端加密（服务端管理密钥）+ 隐私记录权限隔离，零摩擦
- **增强安全**（可选）：客户端 AES-256-GCM 加密（Web Crypto API），密钥永不离开设备，服务端零知识；需生成恢复助记词（12/24词）

**其他安全机制：**

- 操作日志防篡改（禁止 UPDATE/DELETE）
- 关键操作二次确认
- 登录失败 5 次锁定 30 分钟（P0）
- 家庭共享数据按需同步，家人修改需主账户审批

### 9.4 兼容性

- 手机（iOS Safari / Android Chrome）
- 平板（横屏/竖屏）
- 桌面浏览器（Chrome / Firefox / Edge / Safari）

```text
└──────────────┘      │  家庭共享数据池   │      └──────────────┘
                      │  待审批队列       │
                      │  加密配置(密文)   │
                      └──────────────────┘
```

**架构要点：**

- **本地优先（Local-first）**：IndexedDB 为主存储，日常记录默认仅存本地。加入家庭组后，数据按需同步至 PostgreSQL 服务端
- **PostgreSQL 存储**：用户账户、权限、家庭组、审批队列、通知、加密配置（密文）等需要持久化和服务端共享的数据
- **传输加密**：WebSocket over TLS (wss) + HTTPS
- **双安全模式**：普通模式（默认，服务端加密）和增强模式（可选，客户端 AES-256-GCM 零知识加密）
- **Docker Compose 部署**：db (PostgreSQL 17) + api (Uvicorn 0.53+) + web (Node 24 LTS + pnpm build) + nginx (反向代理)

## 十三、验收原则

1. 所有 API 端点必须有对应的 Pydantic 请求/响应模型
2. 所有业务查询必须按 `owner_id` 过滤（owner_id 添加后），确保数据隔离
3. 所有列表端点必须实现分页（默认 20 条/页，最大 100 条，响应含 pagination 信封）
4. 所有金额使用分为单位（Integer），前端展示时转换为元
5. GbRecord 变更必须产生操作日志（target_table='gb_record'，含 before_data/after_data）
6. 前端页面必须适配 mobile/tablet/desktop 三种断点
7. 所有新增功能必须编写验收标准（Given/When/Then 格式）
8. 数据库变更必须通过 Alembic 迁移，禁止手动修改表结构
9. 软删除表（gb_record/daily_record/person/payment_account/guestbook）删除时设置 is_deleted=true + deleted_at，30 天后物理清除
10. 枚举样式字段使用 VARCHAR + 应用层 Literal 校验，不使用数据库 ENUM
11. 独立业务表索引以 `(owner_id, ...)` 开头，关联表索引以 `(guestbook_id, ...)` 开头
