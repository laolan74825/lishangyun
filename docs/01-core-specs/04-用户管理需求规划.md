## 2026-10-01 更新说明（已实现，本文档相关章节以此为准）

**角色体系按 3 级落地，原 5 级方案废止：**

| 角色 | 标识 | 来源 |
| ------ | ------ | ------ |

- 用户 ID 格式改为 创建年份(4位) + 6位流水号（如 2026000001），见迁移 `f7g8h9i0j1k2`。

本文后续章节中涉及的 5 级角色、editor/viewer/auditor、sub_admin 权限点等内容均为历史规划，不再执行。

## 一、概述

### 1.1 背景

当前系统采用本地优先架构（IndexedDB 主存储 + PostgreSQL 云端备份/家庭共享）和双安全模式（普通模式 + 增强零知识加密），已具备基础的用户认证体系（Argon2 密码哈希 + PyJWT 令牌 + 多角色体系），但缺乏完整的用户管理能力，包括：系统管理员的完整职能定义、用户间关系管理（家庭成员）、外部协作授权（礼簿级授权码机制）等。随着系统向多终端、多用户协作方向演进，需要一套完整的用户管理规划来支撑业务需求。

### 1.2 账户模型

系统支持注册任意多个账户，每个账户是一个独立的运作单元：

- **独立注册**：任意终端均可注册新账户，注册后即可独立使用全部记账功能
- **数据隔离**：每个账户拥有独立的人员库、礼簿、日常记录、收款账户等，互不可见
- **家庭组邀请**：任何账户均可创建家庭组并邀请其他已注册账户加入，也可接受其他账户的邀请成为其家庭组成员（一个账户可同时属于多个家庭组）
- **协助收礼**：任何账户均可邀请其他已注册账户协助特定礼簿的收礼/对账工作
- **多重身份**：一个账户可同时是自有家庭组的所有者、他人家庭组的成员、多个礼簿的协助者，各身份互不干扰

### 1.3 目标

构建一套 **分层、安全、灵活** 的用户管理体系，覆盖以下场景：

- 系统级管理（超级管理员 — 仅管理系统运维，不参与任何账簿管理）
- 终端级自治（独立注册、数据隔离、完全自主）
- 家庭级协作（任意账户均可创建家庭组、成员邀请、审批机制）
- 礼簿级授权（临时协作、权限最小化）

### 1.4 利益相关者

| 角色 | 说明 |
| ------ | ------ |
| 超级管理员 | 系统级管理员，仅管理系统运维和配置，不参与任何账簿管理 |
| 子管理员 | 受超级管理员委托，协助管理部分系统职能 |
| 普通用户 | 注册账户的终端用户，拥有私有数据空间，可独立运作也可协作 |
| 家庭成员 | 经邀请加入的用户，可协作维护共享记账本 |
| 临时协作者 | 通过授权码参与特定礼簿记账/对账的外部用户 |

### 2.1 角色定义

| 角色 | 标识 | 来源 | 权限范围 |
| ------ | ------ | ------ | ---------- |
| 超级管理员 | `super_admin` | 系统初始化时创建 | 系统运维管理权限，不参与任何账簿管理 |
| 子管理员 | `sub_admin` | 超级管理员创建 | 被授权的特定系统管理职能 |
| 普通用户 | `user` | 终端自行注册 | 个人数据完全控制，可独立运作也可邀请协作 |
| 家庭成员 | `family_member` | 经邀请+审批通过 | 共享记账本的协作权限 |
| 临时协作者 | `collaborator` | 授权码授权 | 指定礼簿的有限操作权限 |

> **应用层角色与 DB 层角色的映射关系：**
>
> 需求分析（v4.1）在 `users.role` 字段定义了 5 个数据库级角色：`super_admin` / `admin` / `editor` / `viewer` / `auditor`。本文档定义的 5 个应用层角色与 DB 层角色的对应关系如下：
>
> | 应用层角色 | 对应 DB role | 说明 |
> | ----------- | ------------- | ------ |
> | 超级管理员 | `super_admin` | 直接对应，系统初始化时创建 |
> | 子管理员 | `editor`（+权限点） | DB 层仍为 `editor`，通过 `permissions` JSONB 字段授予额外管理权限点（§3.3），应用层据此展示管理界面 |
> | 普通用户 | `editor` | 默认角色，完全控制个人数据 |
> | 家庭成员 | `editor`（上下文角色） | DB 层不变，通过 `family_member` 关联表获得家庭组内协作权限 |
> | 临时协作者 | `editor`（上下文角色） | DB 层不变，通过 `authorization_codes` 绑定获得特定礼簿操作权限 |
>
> **设计原则：** DB 层角色仅控制基础访问级别（`super_admin` 管理 / `editor` 读写 / `viewer` 只读 / `auditor` 审计日志），应用层协作权限（家庭成员、临时协作者）通过关联表 + 权限点机制实现，不扩展 DB 角色枚举。`admin` 角色预留给未来数据管理员场景（管理家庭组和审批），当前阶段由 `super_admin` 直接承担。

## 三、需求一：超级管理员

> **定位：超级管理员是系统级管理员，仅负责系统的管理、维护和配置，不参与任何账簿（礼簿/日常记账）的管理操作。** 超级管理员不能查看、修改、删除任何用户的记账数据，不能创建或管理礼簿，不能协助收礼或对账。

### 3.1 功能清单

| 编号 | 功能 | 优先级 | 说明 |
| ------ | ------ | -------- | ------ |
| SA-01 | 禁用/启用用户 | P0 | 禁用后用户无法登录，数据保留 |
| SA-02 | 创建子管理员 | P0 | 分配子管理员角色及具体权限 |
| SA-03 | 查看系统全局仪表盘 | P0 | 用户总数、活跃用户、近期注册趋势、异常登录 |
| SA-04 | 查看操作审计日志 | P0 | 全系统关键操作日志（登录、数据变更、管理操作） |
| SA-05 | 删除用户（软删除） | P1 | 软删除，数据保留60天，期间可恢复 |
| SA-06 | 恢复已删除用户 | P1 | 60天内管理员可恢复被删除的用户账户及其数据 |
| SA-07 | 系统公告管理 | P1 | 发布系统公告，用户登录后展示 |
| SA-08 | 系统参数配置 | P1 | 注册开关、密码策略、自动锁定时间等全局配置 |
| SA-09 | 强制下线 | P1 | 踢出指定用户的当前会话 |
| SA-10 | 数据备份触发 | P2 | 手动触发全量/增量数据备份 |
| SA-11 | IP 黑白名单 | P2 | 限制或允许特定 IP 段访问 |
| SA-12 | 管理子管理员权限 | P0 | 调整子管理员的授权范围，撤销子管理员身份 |

> **安全原则：密码重置只能由用户本人通过安全邮箱验证码自行操作，管理员无权重置任何用户的密码，确保用户数据安全。**

### 3.2 超级管理员推荐扩展功能

在禁用/启用用户基础上，推荐以下核心管理功能：

**安全管控类：**

- **登录日志审计**：记录所有用户的登录时间、IP、设备，支持异常登录检测
- **强制下线**：发现异常时可立即踢出用户会话
- **IP 访问控制**：黑白名单机制，防止恶意访问
- **密码策略管理**：设置最小长度、复杂度要求、过期策略

**运营管理类：**

- **系统仪表盘**：可视化展示用户增长、活跃度、系统负载
- **系统公告**：向所有用户发布维护通知、功能更新等公告
- **数据备份**：手动或定时触发数据备份，保障数据安全

**子管理员管理类：**

- **权限委托**：为子管理员分配特定管理职能（如下文权限矩阵）
- **行为审计**：记录子管理员的所有管理操作
- **一键撤销**：立即取消子管理员的所有管理权限

### 3.3 子管理员权限矩阵

子管理员的权限由超级管理员按需授予，采用 **权限点** 机制：

| 权限点 | 标识 | 说明 |
| -------- | ------ | ------ |
| 用户查看 | `admin:user:read` | 查看所有用户信息 |
| 用户管理 | `admin:user:write` | 创建、编辑、禁用用户（不含超级管理员） |
| 审计日志 | `admin:audit:read` | 查看操作审计日志 |
| 系统配置 | `admin:config:write` | 修改系统参数配置 |
| 公告管理 | `admin:notice:write` | 发布/编辑系统公告 |
| 数据备份 | `admin:backup:write` | 触发数据备份 |
| 统计查看 | `admin:stats:read` | 查看系统统计数据和仪表盘 |

> 超级管理员拥有全部权限点且不可被修改；子管理员可被分配任意权限点组合。

### 3.4 验收标准

```text
SA-01: Given 超级管理员已登录
       When 禁用用户A
       Then 用户A的is_active设为false，用户A立即无法登录，数据完整保留

SA-02: Given 超级管理员已登录
       When 创建子管理员并授予 admin:user:read 和 admin:audit:read 权限
       Then 子管理员可查看用户列表和审计日志，但无法修改用户或系统配置

SA-03: Given 超级管理员已登录
       When 访问系统仪表盘
       Then 展示用户总数、近7日注册趋势、今日活跃用户数、近24h异常登录告警

SA-05: Given 超级管理员已登录
       When 删除用户A
       Then 用户A标记为软删除状态，数据保留60天，用户A无法登录

SA-06: Given 用户A被删除且未超过60天
       When 管理员恢复用户A
       Then 用户A的账户和数据完全恢复，可正常登录

SA-09: Given 用户A当前已登录
       When 超级管理员对用户A执行强制下线
       Then 用户A的当前JWT被加入黑名单，下次请求返回401
```

## 四、需求二：终端注册与数据隔离

### 4.1 功能清单

| 编号 | 功能 | 优先级 | 说明 |
| ------ | ------ | -------- | ------ |
| REG-01 | 开放注册 | P0 | 任意终端可注册新账户（超级管理员可关闭注册） |
| REG-02 | 用户名唯一 | P0 | 用户名全局唯一，注册时校验 |
| REG-03 | 数据完全隔离 | P0 | 每个用户只能看到自己的数据（人员、记账本、日常记录等） |
| REG-04 | 多终端登录 | P0 | 同一账户可在多个终端登录，数据通过服务端同步，但同一时间仅允许一个终端处于活跃状态 |
| REG-05 | 登录方式 | P0 | 用户名+密码登录，支持密码找回（邮件验证码） |
| REG-06 | 注册信息 | P0 | 必填：用户名、密码、安全邮箱（1~2个）；选填：昵称 |
| REG-07 | 安全邮箱管理 | P0 | 用户可添加/修改/删除安全邮箱，最多2个，用于密码重置验证 |
| REG-08 | 注册审核（可选） | P2 | 超级管理员可开启"注册需审核"模式，新注册用户需管理员批准后激活 |
| REG-09 | 自定义锁定时间 | P0 | 用户可在个人设置中调整自动锁定时间，覆盖系统默认值 |

> **安全邮箱说明：** 每个用户必须设置 1~2 个安全邮箱。密码重置时，系统向安全邮箱发送验证码，由用户本人完成密码重置。管理员无法代替用户重置密码，从制度上保障用户数据安全。

### 4.2 数据隔离模型

```text
用户A的数据空间                    用户B的数据空间
┌──────────────────┐              ┌──────────────────┐
│ 人员库 (persons)  │              │ 人员库 (persons)  │
│ 记账本 (guestbooks)│             │ 记账本 (guestbooks)│
│ 日常记录 (daily)   │             │ 日常记录 (daily)   │
│ 收款账户 (payment) │             │ 收款账户 (payment) │
│ 终端设置           │             │ 终端设置           │
└──────────────────┘              └──────────────────┘
        ↑ 完全隔离，互不可见 ↑
```

**实现要点：**

- 所有数据表增加 `owner_id` 字段（外键关联 users 表）
- API 层通过 JWT 中的 `user_id` 自动过滤，确保只返回当前用户的数据
- 家庭成员共享的数据通过独立的关联表实现，不破坏基础隔离

### 4.3 终端活跃与自动锁定机制

**核心规则：**

- 同一账户可在多个终端登录（手机、电脑、平板等）
- **同一时间仅允许一个终端处于活跃状态**：当用户在终端 A 进行操作时，其他终端自动进入锁定状态
- 锁定的终端需要输入账户密码才能恢复使用

**自动锁定策略：**

| 场景 | 行为 | 说明 |
| ------ | ------ | ------ |
| 无操作超时 | 自动锁定 | 无任何操作（点击、输入等）超过设定时长，终端自动锁定 |
| 其他终端活跃 | 自动锁定 | 当检测到同一账户在其他终端有活跃操作时，当前终端立即锁定 |
| 手动锁定 | 用户主动 | 用户临时离开时，可点击"锁定"按钮立即锁定当前终端 |

**锁定时间配置层级：**

```text
超级管理员设置系统默认值（全局）
        │
        ▼
用户自行设置个人偏好（覆盖默认值）
        │
        ▼
该用户所有终端生效
```

| 配置层级 | 配置者 | 可选值 | 说明 |
|----------|--------|--------|------|
| 系统默认 | 超级管理员 | 15分钟 / 30分钟 / 60分钟 / 120分钟 / 永不 | 在系统参数中配置，所有未自定义的用户使用此默认值 |
| 用户自定义 | 用户本人 | 15分钟 / 30分钟 / 60分钟 / 120分钟 / 永不 / 跟随系统默认 | 在个人设置中调整，优先级高于系统默认值 |

> **优先级：** 用户自定义值 > 系统默认值。用户可选择"跟随系统默认"以恢复使用超级管理员设置的默认值。

**锁定/解锁流程：**

```text
终端A活跃中
    │
    ├─→ 超过设定时长无操作 ──→ 终端A自动锁定 → 显示锁屏界面 → 输入密码解锁
    │
    ├─→ 终端B开始操作 ────→ 终端A立即锁定 → 显示锁屏界面 → 输入密码解锁
    │
    └─→ 用户点击"锁定" ──→ 终端A立即锁定 → 显示锁屏界面 → 输入密码解锁
```

**锁屏界面设计：**

- 显示用户昵称/用户名（脱敏）
- 密码输入框 + 解锁按钮
- "忘记密码？"链接（跳转安全邮箱验证重置流程）
- 背景模糊当前页面内容

**实现要点：**

- 前端通过心跳机制（每 5 分钟）上报活跃状态
- 后端维护每个用户的 `last_active_terminal_id` 和 `last_active_at` 时间戳
- 终端锁定状态存储在前端 localStorage，解锁需向后端验证密码
- 其他终端活跃时通过 WebSocket 或轮询通知当前终端进入锁定

### 4.4 验收标准

```text
REG-01: Given 系统注册功能已开启
        When 新用户在终端提交注册（用户名、密码、安全邮箱）
        Then 创建用户账户，角色为 user，可立即登录

REG-03: Given 用户A和用户B各自有独立的记账数据
        When 用户A调用 API 查询记账本列表
        Then 仅返回 owner_id = 用户A 的记账本，不包含用户B的任何数据
```

## 五、需求三：家庭成员管理

> **多账户独立原则：** 任何已注册账户均可创建家庭组并邀请其他账户加入，也可接受其他账户的邀请成为其家庭组成员。一个账户可同时属于多个家庭组，各家庭组之间相互独立。

### 5.1 功能清单

| 编号 | 功能 | 优先级 | 说明 |
| ------ | ------ | -------- | ------ |
| FM-01 | 创建家庭组与发送邀请 | P0 | 任何账户均可创建家庭组，通过用户名搜索其他已注册账户并发送邀请 |
| FM-02 | 处理邀请 | P0 | 被邀请人可接受/拒绝邀请请求；可同时接受多个不同家庭组的邀请 |
| FM-03 | 家庭成员列表 | P0 | 查看当前家庭组列表及各组的成员与角色 |
| FM-04 | 家庭数据共享 | P0 | 家庭组成员可查看共享数据池中所有非隐私数据（`is_private=false`），隐私记录仅标记者本人可见 |
| FM-05 | 主账户审批 | P0 | 家庭成员对共享数据的修改操作需组所有者通过 `pending_approval` 审批 |
| FM-06 | 移除家庭成员 | P1 | 组所有者可移除成员，成员也可主动退出家庭组 |
| FM-07 | 家庭角色分配 | P1 | 组所有者可为成员设置家庭内角色（记账员/查看者） |
| FM-08 | 邀请链接/二维码 | P2 | 生成邀请链接或二维码，方便面对面邀请 |

### 5.2 工作流程

```text
账户A（独立账户）              账户B（独立账户）              账户C（独立账户）
    │                              │                              │
    │ 1. A 创建家庭组X              │                              │
    │    邀请 B 加入                │                              │
    │ ─────────────────→           │                              │
    │                              │ 2. B 接受邀请                 │
    │                              │    同时 C 也邀请 B             │
    │                              │         加入家庭组Y            │
    │                              │    ←─────────────────         │
    │                              │ 3. B 接受 C 的邀请            │
    │                              │                              │
    │  ← B 同时属于 A 的组X 和 C 的组Y，各组独立运作 →             │
    │                              │                              │
    │ 4. A 也可以接受 D 的邀请，成为 D 的家庭组成员                  │
    │    → 一个账户可拥有多重身份，互不干扰                          │
```

### 5.3 审批机制详细设计

家庭成员对共享数据的操作审批流程：

| 操作类型 | 审批要求 | 说明 |
| ---------- | ---------- | ------ |
| 新增记录 | 需审批 | 记录提交后进入 `pending_approval`(status=pending)，主账户确认后生效 |
| 修改记录 | 需审批 | 修改生成变更草稿（payload），主账户审批通过后应用 |
| 删除记录 | 需审批 | 删除请求需主账户确认 |
| 查看记录 | 无需审批 | 家庭成员可直接查看共享数据池中所有非隐私记录 |

**审批状态流转：**

```text
待审批(pending) ──→ 已通过(approved) ──→ 记录生效，通知提交人
      │
      ├──→ 已拒绝(rejected) ──→ 操作撤销，通知提交人（须填写拒绝原因）
      │
      └──→ 已过期(expired) ──→ 超过30天未处理，自动标记，通知提交人重新提交
```

> **审批规则：** 家人提交的修改在审批前仅存在于 `pending_approval` 表中，不影响家庭共享数据池。审批通过后系统根据 payload 写入对应业务表。待审批超过 30 天未处理的记录自动标记为 `expired`，需提交人重新提交。

### 5.4 数据模型设计

> **表名对齐说明：** 以下表名与需求分析（v4.1）§五 数据模型完全一致。`family_group` + `family_member` 替代原 `family_memberships` 单表设计，支持家庭组独立管理（名称、邀请码等）；`pending_approval` 替代原 `audit_queue`，采用通用 `target_table` + `target_id` 模式覆盖多种业务表；移除原 `shared_guestbooks` 表（家庭共享通过 `family_member` 关联 + `pending_approval` 审批机制实现）。

## 六、需求四：礼簿授权码机制

> **多账户独立原则：** 任何账户均可邀请其他已注册账户协助特定礼簿的收礼和对账。被邀请的协助者保持其账户独立性，仅在授权范围内操作指定礼簿，不影响其自有数据和其他协作关系。

### 6.1 功能清单

| 编号 | 功能 | 优先级 | 说明 |
| ------ | ------ | -------- | ------ |
| AUTH-01 | 生成授权码 | P0 | 指定礼簿、被授权者姓名、被授权者账户ID，生成授权码 |
| AUTH-02 | 授权码绑定账户 | P0 | 被授权者在自己账户中输入授权码和授权账户ID完成绑定 |
| AUTH-03 | 授权记账 | P0 | 被授权人可在指定礼簿中登记收礼记录 |
| AUTH-04 | 授权对账 | P0 | 被授权人只能对自己登记的记录进行对账 |
| AUTH-05 | 授权码管理 | P0 | 查看/撤销已生成的授权码 |
| AUTH-06 | 授权码有效期 | P1 | 生成时可设置有效期（默认到礼簿结束） |
| AUTH-07 | 授权操作日志 | P1 | 记录被授权人的所有操作，便于追溯 |

### 6.2 授权码工作流程

```text
┌────────────────┐                          ┌────────────────┐
│  礼簿所有者(A)  │                          │  协作者(B)     │
└───────┬────────┘                          └───────┬────────┘
        │                                           │
        │ 1. 生成授权码                              │
        │    指定：礼簿、被授权者姓名、               │
        │          被授权者账户ID(B的ID)             │
        │    产出：授权码(如 GR-8K3F2M)              │
        │                                           │
        │ 2. 将授权码告知B ─────────────────────────→ │
        │    （可线下口头告知授权码）                  │
        │                                           │
        │                                    3. B 在自己的账户中
        │                                       输入：授权码 +
        │                                       授权账户ID（A的账户ID）
        │                                       完成绑定验证
        │                                           │
        │                                    4. 系统校验：
        │                                       - 授权码有效且未绑定
        │                                       - 授权账户ID与生成时一致
        │                                       - 当前登录用户=B
        │                                       校验通过，绑定成功
        │                                           │
        │                                    5. B 获得该礼簿的
        │                                       记账和对账权限
        │                                           │
        │                                    6. B 登记收礼记录
        │                                       (标记 agent_name = B的姓名)
        │                                           │
        │                                    7. B 对账
        │                                       只能查看/核对自己登记的记录
        │                                           │
        │ 8. A 可随时撤销授权码                       │
        │    撤销后 B 立即失去权限                    │
```

### 6.3 授权码设计

**授权码格式：** `GR-XXXXXX`（6位字母数字混合，便于口头传递）

**生成时必填信息：**

| 字段 | 必填 | 说明 |
| ------ | ------ | ------ |
| 关联礼簿 | 是 | 授权码对应的礼簿 |
| 被授权者姓名 | 是 | 被授权者的真实姓名，用于标识和记录 |
| 被授权者账户ID | 是 | 被授权者的系统账户ID，绑定时的身份校验依据 |
| 权限范围 | 是 | 记账 / 对账 / 记账+对账 |
| 有效期 | 否 | 默认到礼簿结束，可自定义截止时间 |

> **绑定验证规则：** 被授权者在自己账户中输入授权码时，需同时输入授权账户ID（即授权者的账户ID）。系统校验：授权码有效 + 授权账户ID匹配 + 当前登录用户身份与授权码中记录的被授权者账户ID一致，三者全部通过才完成绑定。

### 6.4 权限限制规则

| 权限 | 被授权人可否操作 | 限制说明 |
| ------ | ----------------- | ---------- |
| 查看礼簿全部记录 | 否 | 只能查看自己登记的记录 |
| 新增收礼记录 | 是 | 自动标记 agent_name 为被授权人姓名 |
| 修改自己的记录 | 是 | 仅限自己登记的记录 |
| 删除自己的记录 | 是 | 仅限自己登记的记录，且需礼簿所有者确认 |
| 对账（核销） | 是 | 仅限自己登记的记录 |
| 修改他人记录 | 否 | 完全隔离 |
| 导出礼簿数据 | 否 | 仅礼簿所有者可导出 |
| 生成新授权码 | 否 | 仅礼簿所有者可生成 |

```text
         When 用户B在自己的账户中输入授权码 GR-8K3F2M 和授权账户ID（用户A的ID）
         Then 系统校验：授权码有效 + 授权账户ID匹配 + 当前用户ID=grantee_account_id
         Then 校验通过，grantee_user_id 绑定为用户B，status 变为 bound
         When 用户C（账户ID≠10086）尝试用同一授权码绑定
         Then 校验失败，提示"授权码与您的账户不匹配"

AUTH-04: Given 用户B已绑定授权码，在礼簿X中登记了3条记录
         When 用户B进入对账页面
         Then 只能看到自己登记的3条记录，无法看到其他人登记的记录
         When 用户B对自己的记录执行对账操作
         Then 对账成功
         When 用户B尝试对账非自己的记录
         Then 操作被拒绝
```

## 十一、风险与缓解

| 风险 | 影响 | 缓解措施 |
| ------ | ------ | ---------- |
| 数据隔离漏洞 | 用户看到他人数据 | API 层统一注入 owner_id 过滤，编写隔离性测试用例 |
| 授权码泄露 | 未授权人员获取记账权限 | 授权码设置有效期 + 一次性绑定 + 被授权者账户ID校验 + 可撤销 |
| 审批队列积压 | 家庭成员操作长期不生效 | 审批超时提醒（30天自动标记 expired）+ 可设置自动通过策略 |
| 子管理员权限过大 | 子管理员滥用管理权限 | 权限最小化原则 + 子管理员操作全量审计 |
| 迁移数据丢失 | 升级过程中数据异常 | 迁移前全量备份 + 迁移脚本可回滚 |
| 多终端锁定竞争 | 网络延迟导致多终端同时活跃 | 心跳机制 + 服务端权威判定 + 前端乐观锁定 |
| 安全邮箱失效 | 用户无法重置密码 | 注册时强制验证邮箱 + 允许设置备用邮箱 |
| 60天数据清理 | 定时任务异常导致数据未清理或误清理 | 清理任务幂等设计 + 清理前日志记录 + 管理员可手动触发 |
