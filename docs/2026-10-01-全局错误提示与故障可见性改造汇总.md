# 2026-10-01 全局错误提示与故障可见性改造汇总

起因：数据库未启动时打开前端页面，数据拿不到但页面无任何提示，用户无法区分「没有数据」和「系统故障」。本次改造让前后端所有请求失败都对用户可见，前后端各为一个独立提交（后端 `feat`：全局异常处理器；前端 `feat`：全局错误提示），均带回归测试并经过真实停库演练验证。

## 一、后端：全局异常处理（`server/app/core/errors.py`）

### 异常分流

| 异常类型 | 响应 | 说明 |
|-|-|-|
| `sqlalchemy.exc.OperationalError` | 503 | 连不上 / 连接丢失（SQLAlchemy 包装后的常见形态） |
| `sqlalchemy.exc.InterfaceError` | 503 | 连接池层面失效（如 pool_pre_ping 探测失败） |
| `DBAPIError` 且 `connection_invalidated` | 503 | 连接已被判定失效的其他数据库错误 |
| 底层 `OSError`（socket.gaierror、ConnectionRefusedError 等） | 503 | db 容器停止时主机名解析失败会以原始 socket 错误直接到达，不复经 SQLAlchemy 包装 |
| 其他未处理异常 | 500 | 中性提示「服务器内部错误，请稍后重试」，堆栈只进日志不外泄 |

- 503 统一返回 `{"detail": "数据库连接失败，请确认数据库服务已启动后重试"}`
- `HTTPException` / `RequestValidationError` 走 FastAPI 自带处理器，MRO 就近匹配不受影响
- 注册入口：`main.py` 的 `register_exception_handlers(app)`

### 测试

- 新增 `server/tests/test_db_error_handler.py`（6 条用例）：503/500 分流、连接失效判定、socket 错误、内部信息不外泄
- 全套后端测试 273 条通过

## 二、前端：全局错误提示

### 新增基础设施

- `web/src/lib/toast-bus.ts`：全局 Toast 事件总线。普通提示相同内容 4 秒内节流去重、5 秒自动消失；`sticky` 提示按 key 去重替换、常驻置顶，由调用方主动撤下
- `web/src/components/GlobalToast.tsx`：统一渲染容器，错误用 danger 红（`#c0392b`），挂载在应用根部（`main.tsx`）

### 错误分级（`web/src/lib/queryClient.ts` 全局钩子）

| 错误 | 提示形式 | 撤下条件 |
|-|-|-|
| 网络不可达（`ApiError status=0`，fetch 抛 TypeError） | 常驻红色横幅「无法连接到服务器，请确认后端服务和数据库已启动」 | 任一请求成功后自动撤下 |
| 后端 503（数据库连接失败） | 常驻红色横幅，文案原样展示后端 detail | 同上 |
| 其他业务错误（4xx/500） | 红色 toast，带状态码与后端 detail | 5 秒自动消失 |

- 所有 react-query 查询/变更的失败自动进入上述流程，页面无需重复写错误处理
- 个别查询确需静默：useQuery 设 `meta: { silent: true }`

### 静默失败点清扫（本次真正修复的 bug）

1. `LoginPage.tsx`：`/auth/status` 请求 `.catch(() => {})` 完全吞错 —— 登录页在故障时静默
2. `api-client.ts` 四个查询函数（`getGuestbookById` / `getPersonById` / `getPaymentAccountById` / `getTerminalSettings`）：失败返回 `undefined`，网络故障被当成「数据不存在」——已改为 404 等业务错误仍返回 undefined，**网络层错误必须抛出**交给全局提示
3. 其余 `.catch(() => {})` 均为后台非关键操作（IndexedDB 缓存写入），保留静默

### 测试

- 新增 `web/src/test/global-toast.test.ts`（11 条用例）：节流去重、自动消失、粘性替换、订阅退订、503 识别、错误描述
- 全套前端测试 174 条通过

## 三、真实环境演练记录

| 场景 | API 响应 | 前端表现 |
|-|-|-|
| 停 api + db 容器 | 502（nginx） | 红色提示「请求失败（502）：Bad Gateway」 |
| 仅停 db 容器 | 503 + 「数据库连接失败，请确认数据库服务已启动后重试」 | 常驻红色横幅，文案与后端一致 |
| 恢复 db | 200 | 横幅自动消失 |

## 四、踩坑记录（后续注意）

1. **测试夹具全局泄漏**：测试里 `app.dependency_overrides.clear()` 会清掉 conftest 在导入期设置的 get_db 全局覆盖，导致同进程后续 154 个测试误连真实数据库。正确做法：保存原覆盖、测试后原样恢复（见 `test_db_error_handler.py` 的 `failing_db_client` 夹具）
2. **PWA 缓存干扰验证**：vite-plugin-pwa 的 Service Worker 会缓存旧版前端，部署后出现「改了没生效」的假象。日常排查先 `Ctrl+F5` 强刷；自动化验证前需注销 SW 并清 caches
3. **nginx 上游 DNS 缓存**：api 容器重建后 IP 变化，nginx 重启前会持续 502。重建 api 容器后必须 `docker compose restart nginx`

## 五、相关提交

- 后端：`feat(后端)` 全局异常处理——数据库连接故障返回503，其余异常500中性提示
- 前端：`feat(前端)` 全局错误提示——故障对用户可见，不再静默失败
