# 文档维护规范

> 本文档定义 `docs/` 目录的组织规则、命名规则、版本规则与归档规则。
> 会话产物的保存规范（改完代码往哪记）见仓库根目录 `AGENTS.md` 第 10 节；文档地图见 `docs/README.md`。

---

## 一、目录结构与职责

| 目录 | 职责 | 可变性 |
|------|------|--------|
| `00-meta/` | 本规范等元信息 | 极少变更 |
| `01-core-specs/` | 核心规范（需求、开发要求、流程、UI、测试），**代码变更须同步** | 随版本演进 |
| `02-plans/` | 专项方案与计划 | 方案落地后转实施汇总 |
| `03-operations/` | 合规、部署、运维 | 上线前高频更新 |
| `04-support/` | 终端用户 FAQ 与技术速查 | 随功能更新 |
| `05-implementation/` | 实施汇总（按日期），只读历史 | 只增不改 |
| `99-archive/` | 已废止文档与早期存档 | 只进不出 |
| `kimi-work-history/` | Kimi Work 完整对话存档 | 按对话追加 |

## 二、命名规则

- **核心规范**：`NN-名称.md`（两位序号，如 `03-礼尚云-需求分析.md`），序号即阅读顺序权重。
- **实施汇总**：`YYYY-MM-DD-主题汇总.md`，落在 `05-implementation/`。
- **专项方案**：`名称.md` 或 `名称方案.md`，落在 `02-plans/`。
- 文件名中的产品名跟随现行品牌（当前为「礼尚云」）；历史文件名不改，移入 `99-archive/` 时保持原样。

## 三、版本规则

1. **应用版本号唯一出处**：`web/package.json` 的 `version` 字段；发版用 `npm run release[:patch]`，脚本自动递增并在 `CHANGELOG.md` 插入条目。
2. **文档版本**：`01-core-specs/` 各文档带 YAML frontmatter（`title` / `version` / `updated` / `status`），内容变更时同步更新 `updated` 与 `version`。
3. **禁止写死过期版本号**：引用其他文档优先用相对超链接；必须写版本号时，同步维护 `docs/README.md` 的版本表。

## 四、更新纪律（代码 ↔ 文档同步）

1. 修改接口、统计口径、权限约束后，第一时间更新 `01-core-specs/` 对应规范。
2. 任何跨模块改动完成后，在 `05-implementation/` 新建当日汇总。
3. 用户可见的功能变化记入 `CHANGELOG.md`「未发布」段，发版时转入正式版本段。
4. 新文档创建或版本变化，当日同步 `docs/README.md` 对应表格。

## 五、归档规则

- 已废止的方案/规范：移入 `99-archive/`，用 `git mv` 保留历史，并在 `99-archive/README.md` 登记。
- `05-implementation/` 与 `kimi-work-history/` 只追加、不修改，保证历史可信。
- 对话存档的粒度：一个完整工作主题（或一个 Kimi Work 对话）一份文件，命名 `YYYY-MM-DD-主题.md`，并在 `kimi-work-history/README.md` 索引中登记主题、轮数、日期。

## 六、AI 会话的文档操作禁区

- 不得删除或改写 `05-implementation/`、`99-archive/`、`kimi-work-history/` 中的历史文件。
- 不得绕过 `AGENTS.md` 第 3 节的命名红线"统一命名"（数据库名 `giftregistry`、前端本地存储标识是刻意保留）。
- 改动 `01-core-specs/` 任何文档后，必须在同一次提交或紧随的提交中同步 `docs/README.md` 版本表。
