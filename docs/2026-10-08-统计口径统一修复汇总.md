# 2026-10-08 统计口径统一修复汇总

起因：统计报表的月度收支趋势把礼簿收礼按**录入时间**（record_time）归属月份，补录历史宴席时趋势错位——9 月宴席的钱显示在 10 月。本次将统计类口径统一为「按数据里的时间（宴席日期）」，共三个独立提交，均带回归测试并部署验证。

## 一、月度收支趋势：按宴席日期归月（`d554e14`）

- `server/app/api/stats.py` 的 `monthly-trend`：礼簿收礼原先 `date_trunc('month', GbRecord.record_time)`，改为 join 所属礼簿后按 `Guestbook.event_date` 归月，与日常收支（本就一直按 `DailyRecord.event_date`）口径一致
- 日常收支、事由分布等其他统计分组本已按数据日期，未动

## 二、统计概览：日期区间按宴席日期筛选（`b7580ea`）

- `stats/overview` 的 `start_date` / `end_date` 区间筛选：礼簿收礼原先按 `record_time` 过滤（还需做本地→UTC 换算），改为按 `Guestbook.event_date` 过滤，多余的时区换算代码一并移除
- 效果：「本月送出/收到」卡片和区间查询中，补录的上月宴席收礼计入上月，不再错进本月

## 三、月度趋势：返回时间正序（`83329e1`）

- 接口原先按月份倒序返回（最新在前），图表从左到右画成「10 月 → 9 月」，补录的早期月份仍排在后面，观感上像没修好
- 改为：查询仍按倒序取最近 N 个月（保证取到的是最新的 N 个月），返回前反转为时间正序；前端图表无需改动，直接按接口顺序从左到右绘制

## 四、口径约定（重要，后续开发请遵守）

| 场景 | 口径 | 理由 |
|-|-|-|
| 统计分组/归月/区间筛选（趋势、概览、事由分布、排行） | 按**数据日期**（日常 event_date / 礼簿宴席日期） | 用户关心「这笔人情发生在什么时候」 |
| 账户对账「今日各账户已收」（`payment_accounts.py` accounts-summary） | 按**录入时间** record_time | 资金口径：关心钱哪天实际到账 |
| 微信账户每日限额用量（`payment_accounts.py` received-today） | 按**录入时间** record_time | 限额按实际收款时间计算，补录历史宴席不应占用今日额度 |
| 人员往来明细列表排序、导出明细的「录入时间」列 | 按 record_time 展示 | 展示事实，非统计口径 |

## 五、测试

  - 今天录入、宴席在上月 → 趋势与概览均计入上月、不计入本月
  - 趋势返回月份严格时间正序，后录入的早期月份排在前面
  - 两个依赖旧口径的既有用例改为对齐宴席日期后再断言
- 修复后全量后端测试 **337 条全部通过**；三次提交均重建 api 镜像部署，接口与首页验证正常
